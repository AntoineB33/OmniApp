# OmniApp Global Architecture

## 1. Architectural Pattern: MVI (Model-View-Intent)
OmniApp utilizes a strict unidirectional MVI architecture. This ensures predictable state management across complex, highly interactive UIs like the Task Scheduler.

* **Model (State):** Immutable data classes representing the absolute truth of the UI. State is held in shared ViewModels.
* **View (Compose):** Stateless, declarative Compose Multi-platform functions. The View observes the State and renders it. It has no decision-making power.
* **Intent (Action/Event):** User interactions (clicks, typing, keyboard shortcuts) are dispatched as Intents to the ViewModel. The ViewModel processes the Intent, executes business logic, and emits a new immutable State.

## 2. Kotlin Multi-platform (KMP) Structure
The codebase follows a "Shared UI, Native Shell" philosophy.

* `shared/commonMain`: Contains 95% of the code. This includes the Domain logic, local database interactions, MVI ViewModels, and the Compose Multi-platform UI.
* `shared/[platform]Main`: Contains `expect`/`actual` implementations for platform-specific APIs (e.g., file system paths, platform-specific thread dispatchers, or lifecycle hooks).
* `[Platform]App`: The lightweight entry points. 
  * `desktopApp`: The primary JVM execution environment.
  * `androidApp`: The Android wrapper (MainActivity).
  * `iosApp`: The SwiftUI wrapper (hosting the Compose UIViewController).
  * `webApp`: The WASM/JS entry points.

## 3. Desktop-First Execution
OmniApp prioritizes Desktop interactions first. 
* Mouse events (hover, drag, right-click) and keyboard modifiers (`Ctrl`, `Shift`, `Tab`) are handled via Compose Multi-platform's `PointerEvent` and `KeyEvent` APIs in `commonMain`.
* When porting to touch interfaces (Android/iOS), adapter logic maps touch gestures (long-press, swipe) to the underlying MVI intents originally designed for mouse/keyboard.

## 4. Local Persistence & Offline-First
OmniApp is entirely offline-capable.
* **Framework:** Local database operations utilize a multi-platform SQL wrapper (SQLDelight); the desktop target uses the SQLite JDBC driver, web targets fall back to browser local-storage.
* **Load + debounced save:** State is loaded from the database once at startup; while running, the in-memory MVI State is the single source of truth. Every mutation updates that State immediately and is written back to the database on a small debounce (the store is not a reactive `Flow` source — the ViewModel does not collect DB queries live).
* **Continuous Sync:** All mutations (including Undo/Redo history units, stored one row per unit) are saved to the local database on that debounce, with a flush on close, to minimize data loss on unexpected exits.

## 5. History Architecture (Undo/Redo Engine)
The Undo/Redo mechanism operates on **Delta-based `HistoryUnits`** kept in one shared, persisted timeline (see §4 and `docs/PRD_TaskScheduler.md` §6 for the authoritative spec).
* Instead of saving full state snapshots (which would cause memory bloat with an infinite tree), the engine stores `HistoryUnits`.
* A `HistoryUnit` carries a `Delta` that is applied to move the state forward/back and inverted for the opposite direction, so the same unit serves both undo and redo.
* The timeline is **grouped into categories** (Edit Mode, Selection, Calendar, Main "the rest", Window-nav), **each with its own pointer** that walks only its own units — there is no single global pointer.
  * `Ctrl + Z` / `Ctrl + Y` walk the category of the **currently focused window** (the tree's edits, or the focused floating window's — e.g. the calendar's).
  * `Alt + Left` / `Alt + Right` walk the **selection-state** changes (task tree only).
  * A new mutation immediately discards the `HistoryUnits` ahead of that category's pointer (branch truncation).

## 6. Testing Strategy (TDD)
Behavior-Driven Development (BDD) and Test-Driven Development (TDD) are strictly enforced, focusing entirely on state mechanics.

* **ViewModel State Testing (Primary):** No UI code is merged without passing tests for the MVI Intent-to-State transitions. 
* **Scope:** Tests must validate selection mechanics, tree nested logic, and history delta generation entirely in memory using Kotlin's `runTest` API.
* **Target Execution:** Core tests reside in `shared/commonTest`. These same tests are executed across all platform targets (JVM, iOS Native, Wasm/JS) via Gradle to guarantee the state engine compiles and runs flawlessly on every architecture.
* **UI Testing:** Compose Multi-platform UI testing (e.g., verifying pixel-perfect rendering or semantic nodes) is deferred. The current mandate is to test the *State*, allowing the UI to remain a simple, stateless reflection of that data.
* **Manual testing:** Behaviour the automated suite cannot reach — real persistence, cross-device sync convergence, presence, OS-scheduled push cues, the background service, per-account isolation — has a step-by-step release checklist in `docs/MANUAL_TESTING.md` (keyed to the `scripts/account*` entry points; subsystem detail delegated to `docs/PAUSE_CUE_DELIVERY.md`).

## 7. Debug Tooling
Debug tooling exists to *exercise the real app under controlled conditions*, never to replace its logic. **Mandate:** any debug control that simulates an event (time passing, a device sleep, etc.) must drive the **same Intents and code paths** the production app uses for that event — it may differ only in the *source* of the trigger; downstream handling must be the production logic, shared, not copied. Controls are gated by `DebugFlags`, set once at startup from the platform entry point and **off by default**, so a packaged/release build never shows the debug tooling. The desktop dev `run` task enables it via the `omniapp.timeSim` system property; `createDistributable` (release) does not, so it ships off.

This is currently realized only by the Task Scheduler's time-simulation panel; its behaviour is specified in `docs/PRD_TaskScheduler.md` (§16).

## 8. Cross-Device Sync & Push Delivery
Cross-device sync is **offline-first**: the local SQLite database (§4) stays the source of truth and the server holds a mirror. The backend is **Supabase** (Postgres + Auth + Edge Functions); the client talks to PostgREST / GoTrue directly over HTTPS. **There is never a WebSocket connection to the server** — and there is no polling, heartbeat, or periodic refresh of any kind. The app initiates a server exchange at exactly **four sync moments**, and those (plus the Edge-Function push channel below) are **the only communications between the app and the server**:

1. **Login / logout** — signing in to the account, which every launch does (interactive sign-in, the scripts' auto-login, or restoring the persisted session at startup), and the user-initiated sign-out. The login reconcile pulls a newer remote snapshot or seeds/pushes the local one. A sign-out first flushes any change still inside a debounce window and runs one **farewell reconcile** — push pending local changes / pull a newer remote — before dropping the session (`TaskSchedulerViewModel.signOut`), so an edit made right before signing out reaches the server instead of stranding locally. Best-effort: an offline farewell still signs out, and the persisted dirty flag sends the change on the next login. The **remote force-logout** path (`account_logout`, detected inside the reconcile) is unchanged — it drops the session pushing nothing. Covered by `SignOutFarewellSyncTest`.
2. **The sync button** — the manual "fetch from server" / "Sync now" control (`TaskSchedulerViewModel.syncNow`).
3. **A user change, on a 10-second trailing debounce** — an *authoritative* local change is mirrored to the server once the user has been quiet for 10 s (`scheduler/sync/ServerPushDebounce`, wired in `TaskSchedulerViewModel`; a burst of edits collapses into one push fired 10 s after its last change). The local SQLite write keeps its own small §4 debounce, and `markDirty()` fires immediately so a change is durable — the next login moment sends it — even if the app closes before the deferred push.
4. **The deferred pause-cue burst at `min(d1, d2) − 1/2 s`** — the last-responsible-moment write described under *pause-end cue delivery* below. Every side channel (pause-cue schedule, presence, active sessions + derived-pause pull) coalesces into this single burst, so it is the only recurring traffic of an untouched session — roughly one small burst per pose cadence, and zero while a pose keeps sliding on the now-line.

  Every reconcile emits a **unified sync moment** (`SchedulerSyncEngine.syncMoments`): the per-row side channels (own active sessions + sleep gaps up, account-wide derived pauses + peer gaps down) run at exactly the moments the snapshot syncs — never on their own schedule. Local scans and session opens/extends/finalizes write only the local store and *ride* the next moment; nothing else ever reaches the network. (The server→device direction is the Edge push; its client-side supports — FCM/APNs token registration when the OS issues a token, the phones' `account_last_phone` claim at startup/first-moment/app-foreground, and the presence read that gates the cue at fire time — are part of that push channel, not extra sync traffic: all are rare, tiny, user-event-driven writes/reads.)

* **Minimal wire payload (reconstructibility rule).** What goes over the wire is the **authoritative projection**, not the full local snapshot: `TaskSchedulerViewModel` binds `SchedulerStateCodec.syncFingerprint` as the push payload, so a `scheduler_snapshot` write carries only data no device can re-derive — the task tree (with records), pinned/user panels, reminders, sleep/settings, history. The **regenerated** panels (`SchedulerDomain.isRegeneratedPanel` = `sideTask || sleep || (auto && !pinned && !chore)`) and the **local-only view state** (`SchedulerState.withLocalViewStateNeutralized()` — focused window, tree selection, calendar display switches, WindowNav/Selection history) are stripped: a puller regenerates the panels on its next §9 reschedule (within ~1 s) and carries its own view state across the pull (`applyRemoteSnapshot` → `withLocalViewStateFrom`). Covered by `SyncPayloadTest`. (The regenerated panels are still written to the *local* SQLite row — recomputed on load, never remote traffic.)
* **Authoritative-change gate (no per-tick heartbeat).** The debounce is only the *timing*; **which** changes push is gated on that same `syncFingerprint`: an engine-tick reschedule that only re-derives the auto/side/sleep panels — or a UI-only change that navigates windows / zooms the calendar / toggles a display switch — leaves the fingerprint unchanged, so it neither `markDirty()`s nor pushes (reconstructibility rule). Only an authoritative change — tree edit, a **manual** record edit, pinned/user panel, reminder check, sleep/settings, history — moves the fingerprint. So an **idle** signed-in session (e.g. the always-on account-3 release with no open window) makes **zero** `scheduler_snapshot` writes; `TaskSchedulerViewModel.scheduleSave`/`flush` consult the gate, `SyncFingerprintGateTest` covers it, and `docs/PAUSE_CUE_DELIVERY.md → Testing E` is the manual check.
* **Server-derived account-wide pauses (Inactivity bands) — implemented.** A *pause* is a window when **no** device on the account was active — active meaning the app is running, signed in, and the screen unlocked/interactive. Each device reports the exact intervals it **was active** via a heartbeat (`SchedulerEngine.launchActiveSessionTracking` samples `isScreenActive()`, opening/extending/finalizing a `device_active_session` row; a real suspension or an inactive screen ends the session, judged from **real** elapsed time so a fast sim tick doesn't fragment it). Rows sync per-row (`ActiveSessionGateway` → `device_active_session`, same outside-the-snapshot separation as `device_sleep_gap`/`device_presence`), pushed **only at the four sync moments** above — the beat that opens/extends/finalizes a session writes the local store only. The **server** deduces the pauses (`derive_pauses(p_since, p_until)` RPC = complement of the UNION of every device's active intervals over the last 168 h — **every** uncovered gap is a pause: leading (a freshly emptied account shows the whole past as one pause), interior, **and trailing**; *inactivity unless a device reported activity*. Session rows carry a **`closed`** flag: a finalized session counts exactly its recorded interval, and only a still-**open** session whose `updated_at` is fresh — within a 3 h grace; an active signed-in device refreshes its row at least once per pose-coalesced burst (≤ ~2 h apart) — is presumed active through `now`. That presumption is what keeps a live-but-quiet peer from reading as a phantom Inactivity band, without fabricating activity after a device that actually stopped: an open row staler than the grace means the device vanished mid-session (crash/offline), and the pause after its recorded end appears retroactively once the grace lapses); the client pulls them **only at the four sync moments** into `SchedulerEngine.inactivityGaps`, drawn as greyed **"Inactivity"** calendar bands and folded into the §15 rest-pose seeding (startup additionally runs a purely **local** derivation from this device's own stored sessions — no network — for a prompt first render while the login reconcile is in flight). **Every remote refresh pushes first, then pulls**: the push uploads this device's full in-horizon history with its open session marked `closed = false`, so the server never hands anyone a pause over a window this device was active, and a live peer's fresh open row covers the window up to a second device's launch server-side — no client-side presumption or pull-first ordering needed. A session **end** (screen off / suspension) finalizes **locally** and rides the next sync moment — in practice the deferred pause-cue burst that lands 1–2 s before the next pose end — so a peer can over-presume this device active for at most one pose cadence (bounded further by the 3 h open-row grace). That bounded staleness is the deliberate price of the four-moments-only rule; it is far tighter than the old failure this design replaced, the "Inactivity band stops an hour before the now-line" incident: a desktop that went quiet right after a sync moment stayed presumed-active, and a phone starting later **durably adopted** that presumption (the old startup-adoption scheme wrote the not-a-pause window into its local store as reserved `SchedulerEngine.REMOTE_ACTIVITY_DEVICE_ID` rows), permanently hiding the genuine pause. That adoption is **retired**: `SchedulerEngine.purgeLegacyAdoptedRows` deletes what older builds wrote at startup, and any not-yet-purged `remote-activity` rows are excluded from the own-activity subtraction and from every upload (`pushableActiveSessions`). Derived pauses are **not** stored server-side (reconstructibility rule) — computed on demand, cached client-side for display; the pure `SchedulerDomain.derivePauses` is the tested reference the SQL mirrors and the signed-out/offline fallback. This supersedes the earlier per-device `device_sleep_gap`-as-band idea (a raw sleep on one device while another was in use is not an account-wide pause); `device_sleep_gap` remains only as a §15 rest-pose seed on OS-log platforms.
  * **Carving the "Sleep" band with activity — implemented (display-only).** The scheduled §17 "Sleep" band no longer always draws solid: where the account was demonstrably **active** during a scheduled sleep window (the user kept working through the night), the band is split to show a **gap**. The carving activity is the complement of the account-wide pauses over `[now − 168 h, now]` (so where there is no pause, someone was active) **plus** this device's own **open** session `[activeSince, now]` — the latter so the band retracts continuously to the now-line while the user works, at the display cadence rather than only at a sync moment. It is **conservative**: only *known* activity carves, so an empty `inactivityGaps` (the startup transient before the first derive, or a store-less web install) carves nothing, and every future/no-evidence window stays solid. This is entirely a **display** transform (`SchedulerDomain.carveSleepPanels`, applied in `App.mergePanelsForDisplay`; the scheduler's obstacle math still treats the whole window as sleep) built from already-derived inputs — it persists and syncs **nothing**, and the continuous retraction as the open session extends is a per-tick local view change that never triggers a push (reconstructibility rule); a peer learns of the same activity only when an unrelated sync moment carries this device's `device_active_session` rows. `SchedulerEngine.activeSince` exposes the open-session start; it moves only on a structural open/finalize, never per tick.
  * **Incremental OS-log backfill.** The launch backfill that records this device's recent OS-recorded sleeps (`SchedulerEngine.backfillSleepGaps`, Windows Kernel-Power log) writes the **local** gaps store only — the rows reach the server on the next sync moment's gap push (`pushOwnRecentSleepGaps`), like every side channel — and no longer re-reads the full 3-day horizon each launch: it resumes from a persisted **"scanned through" checkpoint** and records the current time as the new checkpoint afterward (`SchedulerDomain.sleepScanFloor`; a null/stale checkpoint still clamps to the 3-day floor). The checkpoint is **local-only device scan progress** — never synced, never a History Unit — stored in its own single-row `sleep_scan_checkpoint` SQLite table (schema v7, `SleepScanCheckpointStore`), kept out of `sync_meta` so the sync engine's whole-row `sync_meta` writes can't clobber it.
* **Pause-end voice cue delivery (FCM / APNs) — server + Edge send implemented; client token/schedule wiring is the follow-up.** The server half is `supabase/migrations/` (`device_push_token` / `account_last_phone` / `pause_cue_schedule` + the `tick_pause_cues()` cron and last-phone-change trigger) and the `supabase/functions/pause-cue/` Edge Function, which now performs the **real FCM HTTP v1 and APNs HTTP/2 sends** (OAuth2 / ES256 JWT minted in-function from the `FCM_SERVICE_ACCOUNT` / `APNS_*` secrets). The **shared client wiring and the Android native path are done** (`PauseCueGateway` writes `pause_cue_schedule` / claims `account_last_phone`; `SchedulerEngine` publishes the next pose-end and, on a phone, schedules an exact AlarmManager alarm; `PauseCueMessagingService` registers the FCM token and acts on the data push; the alarm's `onPauseCueFire` re-runs the presence/screen-off gate before speaking). The **iOS** path is **written but unverified** — the `iosMain` platform actuals (`PauseCueLocal.ios` scheduling via `UNUserNotificationCenter` + the previously-missing `Voice`/`DeviceInfo`/`SystemNotifier`/`SleepHistory` actuals), the `IosPushBridge` Swift⇄Kotlin seam, `App()`'s `installPauseCuePushBridge` call, and the Swift `AppDelegate` (APNs registration + push routing) all exist, but Kotlin/Native can only be compiled on a Mac and iOS is still blocked by a pre-existing `ui/CalendarUi.kt` Native-portability bug; iOS also cannot re-run the eligibility gate at a local notification's fire time. What still needs doing: that Mac build/fixup, and your Firebase/Apple credentials + `supabase secrets`. The full runbook is `docs/PAUSE_CUE_DELIVERY.md`. The end of a 5/15-minute pose (`docs/PRD_TaskScheduler.md` §15) is announced by a spoken cue on **a phone** — the **last phone that logged in to the account**. Because a backgrounded phone can't reliably run an in-app timer, the cue is delivered as an **OS-scheduled local notification**:
  * When a change on the **phone itself** moves the next pause-end cue, the phone schedules it locally (an **FCM** data message on Android / **APNs** on iOS) and cancels the previously scheduled one.
  * When the change originates on **another device** (e.g. the desktop), that device syncs to the server; **one minute before** the cue is due, a Supabase **Edge Function** pushes the last phone (FCM/APNs) to schedule the cue at the exact instant. The server **skips** this push when the pending next-cue schedule is itself due to a change *the phone* made (the phone has already scheduled it).
  * **Deferred, last-responsible-moment push (no per-change chatter).** The client does **not** write `pause_cue_schedule` on every prediction change (there is no heartbeat). It compares **d1** — the instant the server already holds, seeded from the row at startup and then tracked — with **d2**, this device's current next-pose-end, and upserts only at **`min(d1, d2) − margin`**: a **2 s** margin when `d2 > d1` (the server's *earlier* instant would fire the phone too early, so its stale alarm must be **cancelled** — the upsert's trigger → edge push needs ~1 s to reach the phone plus ~1 s of slack), else **1 s** (nothing stale to cancel — the cue is moving earlier, or it's the first publish). When `d1 == d2` it never pushes — an idle session makes **zero** cue writes; the `tick_pause_cues` cron stays the ~1-min-before backstop. A pose the user is **working through** (screen active) is *pinned to the now-line* (`SchedulerDomain.sideTaskNextStart` clamps an overdue rest to `now`), so `d2 = now + duration` climbs on every engine tick and `d1 != d2` — yet this **still** doesn't chatter: each tick's new prediction **re-arms the single timer** with `wait = duration − margin` (≈299 s for the 5-min pose), far longer than the ≤30 s advance-tick cadence, so the timer is cancelled and re-armed long *before* it could fire. On a freshly-emptied account (`d1` null, e.g. after `account1-empty-and-open`) the push therefore **never fires while the pose keeps sliding** — zero writes; only once `d2` stabilises on a real upcoming pause does exactly one write land, at `d2 − 1 s`. (`PauseCuePushSchedulerTest.a_pose_pinned_to_the_now_line_never_pushes` covers it.) Implemented by `scheduler/sync/PauseCuePushScheduler`, driven from `SchedulerEngine.launchPauseCueSchedule`; the phone's own local OS cue is still (re)scheduled **immediately**, independent of this deferred server write. The cross-device **presence** write (this device's "active screen", used by the phone's screen-off suppression gate) is **coalesced into this same burst** — published once at `min(d1, d2) − margin`, right before the pose end the phone reads it at — rather than by a periodic beacon. There is **no 60 s presence poll**: an idle/working signed-in session makes zero `device_presence` writes outside these last-responsible-moment bursts.
* **Last-phone tracking.** On app start a device calls the server to pull changes; when the caller is a **phone**, that call also registers it as the account's **last logged-in phone**. If the previous last-phone was a different device, the server sends *it* an Edge push to **cancel** its scheduled pause-end cue, so only one phone ever speaks.
