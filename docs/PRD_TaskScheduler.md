## Problem statement

Keeping a long list of competing commitments in proportion is arithmetic nobody does by hand. Deciding "50% of my time on job hunting, 20% on Spanish" is easy; *dividing actual weeks that way* is not. Three failures compound:

* **Drift.** Without a plan in front of you, attention goes to whatever is loudest rather than to what you decided mattered. The shares you intended and the shares you get diverge silently, and nothing tells you by how much.
* **Re-planning cost.** Every fixed commitment, missed block or changed priority invalidates the plan. Redoing that arithmetic by hand after each disturbance is more work than the plan is worth, so it stops being done.
* **Uninterrupted screen time.** The same person who loses track of proportions also sits at a screen for hours. Generic break timers fail because they cannot tell a break that was *taken* from one that merely *elapsed* — so they either nag through breaks already taken or silently forgive breaks that were not.

## Objective and value proposition

Turn a declared set of priorities into a calendar that is continuously correct, and keep the user's eyes out of it.

* **A plan the user does not maintain.** The user states weights and minimum block lengths; the app produces a schedule in which every task converges on its intended share of time at the smallest scale the minima allow, compensates a bounded amount for time lost to fixed commitments, and re-plans **only when something it depends on actually changes** — never merely because time passed (§9; `ARCHITECTURE.md` §3).
* **Breaks that are owed, not merely scheduled.** A break the user did not take stays owed and slides at the now-line until a real pause discharges it, judged from the account's *observed* device activity across every device — not from an assumption that a timer expiring means a break happened (§15).
* **Correct off the device.** If the user walks away from every device with a break due, the phone announces when the break is over, with the app closed (§15; [`docs/PAUSE_CUE_DELIVERY.md`](PAUSE_CUE_DELIVERY.md)).
* **No dependence on connectivity.** The local database is the source of truth; the network is an optimisation ([`PRD.md`](../PRD.md) §5).

**Why now:** the shell — accounts, offline-first persistence, undo/redo, floating windows, cross-device sync — reached the point where a scheduling page can rely on it instead of reimplementing it. Every one of those capabilities is shared with the pages planned for v2.0.0+.

## Success metrics

This is a personal-scale tool that **collects no telemetry**, so there are no adoption, retention or revenue metrics, and inventing them would be dishonest. What is measured instead is whether the product's own promises hold — observable from the user's own data (`scripts/collect-diagnostics.bat`, the History window, the calendar's records) and pinned by tests.

| Promise | Metric | Target |
| --- | --- | --- |
| Shares converge | Realized share of time per task over a rolling window vs. its declared absolute priority (§5, §9) | Within a few percent for tasks schedulable throughout; a task must never sit an order of magnitude below its target |
| The model stays faithful | `side-dev/rules_snapshot.txt` diff under `uv run tests_displayer.py --verify`; `SchedulerPlanTest` replaying the reference cases slot for slot | Zero unexplained diffs — a deliberate change is a *blessed* snapshot, never a silent one |
| Breaks are honoured | Share of due screen breaks actually served (a look-away conducted, a pose discharged by an observed pause), readable from the taken-break panels on the calendar (§15) | Every due break is either served or still visibly owed; none silently expires |
| Cues are exact | Boundary crossings fire **exactly once, in order**; count of crossings logged as *swallowed as stale* in `diagnostics.log` | Zero stale-swallows on a device that stayed awake; any swallow must correspond to a real process suspension |
| Time passing is not a rule change | Schedule fills per hour on an idle account; server writes per day caused by time alone | ≤1 fill/hour (the staleness bound); **0** snapshot pushes |
| Concurrent edits survive | Lost-edit incidents when two devices edit inside one debounce window (`ARCHITECTURE.md` §8.1) | Zero — both edits present after the merge |
| The UI stays responsive on real data | First frame presented on a large, valid database; per-tick recompute cost | Cost follows the **visible window**, never total account history |
| It fits the free tier | Supabase egress and Edge invocations for one phone plus one desktop | Comfortably inside the free plan's limits |

## Scope boundaries

### In scope for 1.6.0

* No-screen and inactivity calendar periods as first-class user-authored entities, with automatic override/trim against on-screen task panels (§8).
* Screen-switch enforcement in the scheduler: on-screen tasks placed only outside no-screen periods, off-screen tasks only inside them; each screen break declares which kind of period it is (§9, §15).
* Past no-screen spans banking **no** record and materializing as real "Inactivity" panels; past sleep persisted as recorded fact rather than projected from the schedule (§9, §12, §17).
* Screen breaks renamed from "side tasks" throughout — UI, documentation, code identifiers and persisted keys — with existing databases still loading (§15).
* Every screen break **slides while owed**, with each cue keyed on the fixed due instant, and three explicit ways a break can be served (§15).
* Phone activity as an unlock/foreground-gated presence heartbeat, and server-side pause-cue delivery over pg_cron plus two Edge Functions (§15).
* Phone calendar gestures: double-tap-and-drag zoom, double-tap contextual menu with panel info, and a menu-driven move (§8).
* Alarms — wall-clock, per-day, synced to every device, rung locally on both phone and desktop (§18).
* Named alternative task trees, and **dated** trees as priority keyframes the scheduler blends between (`ARCHITECTURE.md` §3.1).
* A **default sub-tree** grafted under every newly created task, each of its rows either minting a fresh task id or pointing at an existing one (§4, §7).
* Bidirectional automatic snapshot sync with a **three-way merge** of concurrent edits, last-write-wins surviving only as a fallback (`ARCHITECTURE.md` §8.1).

### Explicitly out of scope

* **Multi-user anything.** No sharing, no collaboration, no permissions. An account is one person's data across their own devices. (Real-time collaboration is [`PRD.md`](../PRD.md) §6's v3.0.0.)
* **iOS ringing and push.** The iOS activity signal and push path are unimplemented and stay so until a Mac build exists.
* **Telemetry and analytics.** Nothing is collected or transmitted beyond the user's own synced state.
* **Accessibility and localization.** Screen-reader semantics, keyboard-only parity beyond the documented shortcuts, high-contrast themes and translation are not addressed in this release. See *Risks*.
* **Additional pages.** Anything reached from the top-left navigation other than the Task Scheduler is v2.0.0+ ([`PRD.md`](../PRD.md) §6).
* **Web persistence parity.** The web target falls back to browser local storage; it is not a supported primary device.
* **User-editable scheduling rules.** The scheduling model (§9) and the screen-break configuration (§15) are fixed; the knobs in §16 are development tooling, not a product surface.

## Target audience

* **Primary — the self-directed knowledge worker with too many parallel commitments** (the maintainer is the reference user). Comfortable with spreadsheets, willing to state priorities numerically, working long unstructured stretches at a computer, using at least one desktop plus one phone. Wants a plan produced *for* them, not a planner to operate.
* **Secondary — the same user away from the desk.** On the phone the app is consulted, checked off, and above all *heard*: the pause cue must work with the app closed.
* **Non-audience.** Teams, managers assigning work, and anyone wanting a to-do list rather than a time allocator. Someone unwilling to attach numbers to their commitments gets nothing from the core model.

## Primary user flows

1. **Declare what matters.** Build the tree (§1–§4), give each cell a weight, read the resulting absolute percentage beside it (§5). *Outcome:* a priority distribution summing to 100%.
2. **Constrain how it may be spent.** Set each task's minimum block length (§10) and its on-screen / off-screen / doable-during-a-break flags (§8, §9); set the nightly sleep window (§17).
3. **Read the plan.** Open the calendar week (§8). The scheduler has already filled it so shares converge; screen breaks and sleep are drawn; nothing is asked of the user. *Outcome:* the next thing to work on is on screen.
4. **Steer it.** Pin a block, drag or resize a panel, add a manual entry, mark a period no-screen or inactive (§8, §11). Each is a rule change: the plan re-derives around it, and `Ctrl+Z` walks it back (§6).
5. **Live in it.** Notifications say when to switch task (§11); voice cues and notifications announce each screen break's start and end (§15); alarms ring (§18); reminders stack on the now-line when overdue (§14).
6. **Take a break — or be told one is still owed.** A break actually taken (observed as a pause across the account's devices) discharges it; one that merely elapsed stays owed and slides at the now-line (§15).
7. **Walk away entirely.** With every device idle and a break due, the phone announces the break's end from the server (§15).
8. **Continue on another device.** Any device signed in to the account shows the same tree, calendar and history; concurrent edits merge rather than overwrite ([`PRD.md`](../PRD.md) §5).
9. **Look back.** The calendar shows what was actually done (§12, §13); the History window shows every change and every notification posted (§6, §11).

## Non-functional requirements

* **Correctness of time-based triggers.** Every notification, voice cue and alarm must be a pure function of which boundary instants the clock crossed — each firing exactly once, in order — never of how a sweep happens to align with the calendar. Staleness is judged only by a crossing's **real** age (a 2 s budget for cues, 60 s for alarms), and consecutive scans must tile the timeline so a clock jump cannot silently clip a crossing.
* **Determinism.** Given the same authoritative inputs and the same `now`, every device must produce the same schedule, the same records and the same break anchors. Nothing derived may depend on device-local ordering or on when a device happened to be running.
* **Performance — cost follows the screen.** Anything recomputed on the display tick must be bounded by the **visible window**, never by total account history. The schedule horizon follows the displayed week (24 h floor, 168 h ceiling); a distant week fills off the UI thread behind a "Calculating…" hint and is not retained.
* **Offline-first.** Every feature except cross-device sync and the server-side pause cue must work with no network, indefinitely — including on a first launch that cannot yet reach the server.
* **Data durability and backward compatibility.** No release may make an existing on-disk database unreadable. Payloads written by earlier shapes decode with defaults, and states an older build wrote that current invariants forbid are **healed on load** rather than surfaced as anomalies. Schema upgrades preserve every row.
* **Persist and sync only what cannot be recomputed.** Derived state — the automatic schedule, banked records, every projection — is recomputed rather than stored or pushed; an always-running device must make **zero** snapshot writes from time passing alone.
* **Privacy.** No telemetry and no third-party analytics. The only data leaving the device is the user's own state, to their own account, plus the device-presence rows the cue needs. The server half is self-hostable.
* **Security.** All server access is authenticated per user and enforced by row-level security; a device belongs to exactly one account at a time, enforced server-side. Service-role paths are reachable only by the cron, never by a client.
* **Cost.** Steady-state traffic must keep one phone plus one desktop inside Supabase's free plan. Egress is the metered axis, not request count.
* **Battery.** No polling while the device is locked: presence ticks only while signed in and unlocked, and the phone arms OS-level alarms rather than staying awake for them.
* **Platform fit.** Desktop interaction (mouse modifiers, complex selection, keyboard navigation) is the reference model; touch gestures are adapted rather than ported ([`PRD.md`](../PRD.md) §2, §3).
* **Verifiability.** Behaviour is asserted against the state holders before any UI exists for it; `./gradlew :shared:jvmTest` is the gate. A field problem must be diagnosable from `scripts/collect-diagnostics.bat` alone.
* **Declared gap:** accessibility (screen-reader semantics, high-contrast themes) and localization are neither specified nor tested in this release. This is a deliberate omission, not an oversight — see *Risks*.

## Risks and mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| **Two independent deployment surfaces** (Supabase and the client apps) drift apart — a migration that changes an RPC signature breaks un-rebuilt clients, and vice versa | Sync or cue silently broken while every test is green | Every change states which surface it needs; `deploy-supabase.bat` applies migrations, both Edge Functions and the cron in one run; a passing test suite is never treated as evidence that a change is live |
| **The live cue path is not fully verified on device** — the heartbeat ↔ cron ↔ Edge ↔ phone chain has unit-tested halves but end-to-end confirmation is outstanding | The away-from-desk promise could fail in the field | The runbook in [`docs/PAUSE_CUE_DELIVERY.md`](PAUSE_CUE_DELIVERY.md); the `scripts/*fast-break*` entry points compress a break to seconds for on-device testing; `collect-diagnostics.bat` merges the phone and desktop timelines |
| **The iOS activity signal is unimplemented** (hardcoded inactive) | iOS devices never contribute presence and never ring; an iOS-only user gets no cue | iOS is explicitly out of scope for 1.6.0; the seam exists and is the only thing to fill once a Mac build is possible |
| **Realtime streaming replays nothing** — a change landing while a device is disconnected is lost to it permanently | The device sits stale, and its next edit is then overwritten by a pull | Every (re)subscribe and every launch performs a catch-up reconcile, bounding staleness by the reconnect instead of by the next user action |
| **A merge cannot always be attempted** — with no common ancestor on record, sync falls back to last-write-wins | One side's work can still be lost in that narrow case | The fallback is confined to a first sync or an upgraded database, logged to diagnostics, and self-healing (the pull it performs records an ancestor for next time) |
| **Aggressive OEM background management on Android** kills the app or defers its work | Presence stops; breaks and alarms are missed | Foreground service, boot receiver, and a one-time Doze-exemption plus autostart prompt; a force-stopped app is a documented limitation, since the OS suppresses delivery until relaunch |
| **Display cost growing with account history** rather than with the visible window | On a large but valid database the window is created and never shown — indistinguishable from a crash | The horizon follows the displayed week; the observed now-line is quantized; distant weeks fill off the UI thread and are discarded; stated as a non-functional requirement and enforced in review |
| **Model complexity** — the scheduling rules are subtle enough that a plausible change can be quietly wrong | Shares silently stop converging, with no user-visible error | One reference implementation; a frozen answer snapshot that fails with a diff on any change; a Kotlin port replaying every reference case; a single copy of the rules with thin drivers over it |
| **Free-tier limits** exceeded by a change that introduces periodic traffic | Sync and cue delivery stop | Event-driven writes only — no timer-driven server traffic — and egress treated as the metered axis |
| **Single maintainer**: no review partner, no bus factor | Undocumented decisions become unrecoverable | Decision records kept inline beside the rule they justify and indexed in [`ARCHITECTURE.md`](../ARCHITECTURE.md) §11; every regression pinned by a named test |
| **Accessibility and localization unaddressed** | The app is unusable with a screen reader, and English-only | Accepted for this release and declared out of scope; not blocked architecturally, since the UI is stateless and replaceable per platform |

*Sections 1–18 below are the **functional requirements** for the Task Scheduler page.*

## 1. Overview

The Task Scheduler is a heavily interactive, infinitely nestable list of cells. It borrows interaction paradigms from spreadsheet applications (like Google Sheets) while applying them to a hierarchical tree structure. This version targets Windows desktop, but stays cross-platform as much as possible.

A single task can exist in multiple cells across the tree. For example: to "find a job," one must "practice English," and to "socialize abroad," one must also "practice English." Two cells sharing the same `taskId` will perfectly mirror the same sub-tree. 
* **Constraint 1:** A `taskId` cannot appear multiple times within the exact same list (this would create conflicting priority values for the same parent task).
* **Constraint 2:** A cell's `taskId` cannot match the `taskId` of any of its ancestor cells (to prevent infinite recursive cycles).
* **Constraint 3:** Multiple unique `taskIds` can share the same title string (e.g., "watch Youtube" under "learn to cook" is a different `taskId` than "watch Youtube" under "learn Spanish").

## 2. Structural UI & Aesthetics

* **Infinite Tree View:** Cells are displayed in a vertical list. The rendered UI tree is strictly synced with the underlying `Map` Tree. 
* **Nesting UI:** The left side of the cells features arrows (if there is a populated sub-tree) and guide-lines (if the cell is expanded) illustrating the parent-child hierarchy. The "root" cell conceptually exists, but the viewport only renders its children.
* **Collapsibility:** Clicking structural arrows toggles the visibility of a cell's sub-list.
* **Visual Aesthetics:** Cell aesthetics strictly mirror Google Sheets. This includes standard resting states, active selection borders/highlighting, and inline editing UI.
* **Priority Display:** The absolute priority percentage is displayed at the right side of the cell. In a sub-list, it is displayed at the same horizontal position. The length between the beginning of the text content and the display of the priority percentage is the maximum of the horizontal lengths of the cell text contents of the sub-list, constrained by a minimum and maximum length. If the text content is too long, the exceeding part is hidden with a little red arrow to the right. This happens even if the cell is in Edit Mode.

## 3. Selection Mechanics (Spreadsheet Paradigm)

The application maintains a dual-state selection model: **Main Selection** (a single active cell or null) and a **Selected Cells List** (a collection of active cells). *Note: Hidden/collapsed cells are ignored during vertical traversal for selection calculations.*

* **Root and Main Cells:** The "root" and "main" cells cannot be selected, edited, or interacted with via mouse events. The "root" cell is only conceptual.
* **Single Click:** The *Selected Cells List* is reset and the clicked cell becomes the *Main Selection*.
* **Single Click & Drag:** * The initial click establishes the *Main Selection*.
  * While dragging without releasing the click, the *Selected Cells List* dynamically spans all visible cells from the Main Selection to the cell currently closest to the cursor.
* **Double Click & Drag:** * If the cell the user double-clicks on is selected and all the selected cells are sequential and in the same sub-list, the whole selection is moved. Otherwise, the double-click empties the *Selected Cells List* then establishes the *Main Selection*.
  * While dragging without releasing the click, the cell gets a grey background and a horizontal blue line between cells indicates where the selection will be placed if the user releases the click. If the changes happen in sub-trees that are mirrored elsewhere (because of sharing `taskIds`), then the change is synced only when the move is finished (the blue line and grey background aren't mirrored).
* **Ctrl + Click:** The clicked cell becomes the *Main Selection* (standard OS `Ctrl` behavior applies for isolated multi-selection).
* **Shift + Click / Ctrl + Shift + Click:** The *Selected Cells List* expands to include all visible cells sequentially from the current *Main Selection* to the newly clicked cell.
* **Up / Left:** Resets selection, and if there is a selectable cell above the main selection, makes it the main selection. Doesn't work when in Editing Mode.
* **Down / Right:** Resets selection, and if there is a selectable cell below the main selection, makes it the main selection. Doesn't work when in Editing Mode.
* **Shift + Direction:** Pressing `Shift` while navigating with the direction keyboard keys allow to select a range of cells. `Right` is `Down` and `Left`. If several cells were selected before pressing `Shift`, it is reset. 
* **Enter or Tab:** If there are several selected cells, moves the main selection among them, from top to bottom then back on top. With `Shift` pressed, it moves backward.
* **Ctrl + A:** Ctrl + A selects all visible cells.


## 4. Editing Mechanics

### Entering Edit Mode
* **Double-click:** Enters Edit Mode on the target cell.
* **Enter or Shift + Enter:** Enters Edit Mode on the target cell if there is only one selected cell.
* **Typing:** If a cell is the *Main Selection* (and not the "root" or "main" cell), typing immediately enters Edit Mode and captures the keystroke.
  * *Dead keys:* A dead key (accent composition such as `^`, `¨`, `~`) enters Edit Mode on an empty cell so the following letter composes into it (e.g. `^` then `e` yields `ê`).

### Active Edit Mode Behavior
While in Edit Mode, *Selected Cells List* resets with only the *Main Selection* and two contextual menus remain visible until editing concludes:

**Menu 1: Mode Selector ("Change Task" vs. "Rename")**
* **Change Task (Default):** A task menu displays existing `taskIds` matching the cell's current text. The menu doesn't appear if there is only one element. There is always one of the elements that is selected. 
  * *Presentation:* The first `taskId` is represented by "New task". The other `taskIds` are represented by their shortest path in the Task Tree (or a list of child titles if no cells point to it).
  * *Filtering:* Impossible IDs (already in the same list, or in the cell's ancestor path) are hidden.
  * *Creation:* Typing dynamically resolves the selection (see *Default selection*). Explicitly selecting the first element (labelled "New task") creates a *new* `taskId` and the cell gets assigned to it, even when the typed title matches an existing task.
  * *Default selection:* When re-entering Edit Mode on an assigned cell, the default selection is the current task of the cell. While typing, the default selection is the **first eligible `taskId`** of the menu — i.e. the first existing task that is *not* in the same sub-list and *not* in the cell's ancestor path (the first row after "New task") — and the cell **reuses** it; only when there are no such tasks does it fall back to "New task" (creating a new `taskId`). This matches the calendar edit window (§8).
  * *Sorting:* Shortest to longest path length -> alphabetical by path -> alphabetical by child titles.
  * *Cleanup:* If a task with no children loses all cell pointers and has no task record (section 8), it is purged from the Task Tree.
* **Rename:** Modifying the text updates the title field in the global `Tree`. *All* cells sharing this `taskId` will temporarily reflect the new text. If the mode is switched back or canceled, other cells revert to their original state.

**Menu 2: Title Suggestions**
* Displays a list of existing task titles similar to the current input (except the exact same title).
* *Sorting:* String similarity -> alphabetical -> number of `taskIds` sharing the title -> total occurrence count.
* *Action:* Selecting a suggestion updates the cell text, but keeps the cell in Edit Mode with menus active.

### Editor Interactions & UI
* **Auto-Save:** Every keystroke/change is immediately committed to the state.
* **Sub-list Syncing:** Edits to a sub-list immediately update all expanded instances of that `taskId` across the UI.
* **Line Breaks:** `Ctrl + Enter` adds a new line. The cell dynamically expands horizontally and vertically to fit the content. 
* **Up and Down:** `Up` goes to the beginning if there is no line above in the cell, and `Down` to the end if there is no line below in the cell.
* **Cancel:** Pressing `Escape` inside Edit Mode cancels the session, reverting all affected cells to their pre edit mode text.
* **Forced Exit:** Changing global selection via mouse click outside the cell forcibly exits Edit Mode.
* **Auto-Expansion:** When the bottom cell of a list receives text, the system automatically:
  1. Initializes a hidden sub-list for it (containing one empty cell).
  2. Appends a new empty placeholder cell directly below it at the current hierarchical level.

### Exiting Edit Mode (Keyboard Navigation)
* `Enter`: moves *Main Selection* down one cell.
* `Shift + Enter`: moves *Main Selection* up one cell.
* `Tab`: If the current cell is populated, opens its sub-list and moves *Main Selection* to its first child. Otherwise, behaves identically to `Enter`.
* `Shift + Tab`: Behaves identically to `Shift + Enter`.
* `Escape`: Cancels the session, reverting all affected cells to their pre edit mode text (see **Cancel**).

### Empty cells management
* **Cleanup:** Empty cells are automatically removed upon exit, *unless* it is the absolute bottom cell of a sub-list.

### Edition without Edition Mode
* **Deletion:** When the user presses `Backspace` or `Delete` and no cell is in Edition Mode, all selected cells get emptied.
* **Copy/paste:** If the selection is consecutive cells, then Ctrl + C copy the selection. It convert the tree structure of the selection and **everything under the selected cells** — the **entire** sub-tree, however deep it runs — into a text. (The maximum depth of §13's *deep copy* is that window's number, not the chord's: Ctrl + C never cuts a sub-tree short and never opens a window.) **The copied text must be readable.** Each task is a tab-indented **title line**; one level deeper, everything the task holds is a named `- <field>: <value>` line — its minimum time (§10), its priority weight table values, and everything the §13 edit window holds (the screen switch, the schedule unit, the text) — with the schedule unit as one `- <step>: <n> min` line per step a level deeper still, and the task **text written out verbatim** in its own indented block rather than escaped onto one line. Every field at its default value is left out, so an untouched task is a title and its minimum time. **The priority weight table of every sub-list the copy walks travels with it**: each task's line carries its own value row, and a task with copied children also carries that sub-list's **weight column header**, so pasting the sub-tree back rebuilds the tables and not merely the titles. What each task carries is governed by §13's three deep-copy switches (ids / priority tables / text). Ctrl + V with a single cell selected allows to paste the copied tree structure only if the text has the right format. In Edit Mode, Ctrl + C and Ctrl + V have the usual behavior.

### Find & replace
* **Ctrl + F opens a find bar in the top-right corner of the tree**, laid out like VS Code's: a query field, a match counter ("3 of 12", or "No results"), the two toggles **Match Case** (`Aa`) and **Match Whole Word** (`[ab]`), the `↑` / `↓` arrows, a close button, and — behind the chevron on the left — a second row holding the **replacement field** with its **Replace** and **Replace All** buttons. Pressed again while open, `Ctrl + F` re-focuses the field and selects what is in it, so a new query overtypes the old one. `Escape` closes the bar and hands the keyboard back to the tree.
* **It searches the whole tree, not the rows on screen.** A task tree is mostly collapsed, so a search restricted to visible rows would miss most of the account. Every hit of the query is shaded in place, and the one the bar is sitting on is shaded more strongly.
* **A match is a range inside one cell's title**, as in a text editor: `aa` in `banana` is two matches, and a title matched twice is two entries in the counter. A **mirrored** task is a row of its own wherever it appears, but its sub-list is walked once — the same children are not counted once per parent.
* **Navigating to a match brings it on screen**: every collapsed ancestor along its own path is expanded, the row is selected in *that* copy of the tree, and the tree scrolls to it. The whole path is **one History Unit**, so walking the matches never buries `Ctrl + Z` under a pile of expand/collapse steps. Typing in the query field does **not** jump — the shading is the live feedback — so `Enter` / `↓` lands on the first match and steps on from there (`Shift + Enter` / `↑` go backwards, both wrapping).
* **Replacing means renaming, exactly as Rename mode does**: the **task's** title changes, so every cell pointing at it follows. **Replace** rewrites the current match's range alone; **Replace All** rewrites every hit of every matched task — **once per task** — as a single History Unit. A replacement that consumes a whole title leaves a blank one, and *Deletion* then applies as usual: the blank title is what deletes.

### Default sub-tree
* **What it is:** A **template sub-tree that always appears under a newly added leaf** — i.e. under every task the user creates by typing a title into an empty cell. It is edited in its own floating **"Default sub-tree"** window, opened from a lateral-menu button (§7), and a **switch to the left of that button** says whether the policy is **currently applied**. The template is one per account: authoritative user data, persisted and synced like the alarms (§18), and shared by every task tree (§6).
* **The window:** **the task tree, drawn by the task tree's own code** — the same cell chrome, the same indentation and hierarchy guide-lines (§2), the same expand arrows, the same percentage and minimum-time columns — with **one little switch added to every non-empty cell** (below), and nothing else changed. It is *edited* the same way too, because it is the same component: a click selects, a double-click on the title — or simply typing on the selected row — opens Edit Mode in place with the ordinary naming menus (a **Tasks** identity menu, then **Title suggestions**), `Enter` / `Shift + Enter` step down and up, `Tab` steps into the child, `Ctrl + Enter` breaks the line, `Backspace` / `Delete` empties, multi-selection and drag-move work, `Ctrl + C` / `Ctrl + X` / `Ctrl + V` copy and paste, `Ctrl + F` searches, and **right-clicking a row opens the same §13 contextual menu** — *start this task now*, *edit*, *copy*, *deep copy*, *add default sub-tree*. A titled row grows a trailing empty child row and a trailing empty sibling (*Auto-Expansion*, above), so the template is built by typing rather than by pressing "add". There is **no bin button** — **the blank title is what deletes**, here as in the tree.
* **The template is a real tree of real tasks**, which is what makes all of that possible: a template row has a task behind it for the menu to act on. So "edit" writes that task's screen switch, schedule unit and text, the row carries a **minimum time** (§10) and a **priority percentage** within the template (§5), and the graft carries all of it across — the fields, the minimum time, and each sub-list's weight table — so a template that says how work splits grafts those proportions rather than a flat list. The percentage is the row's share *within the template*, never a share of the account's tree.
* **Template rows open expanded** — the template is small by design and the window has to show what will actually be grafted (and the trailing empty child row is how the next level is typed) — while a bound row's borrowed sub-tree (below) opens **collapsed**, because a real task's sub-tree can be arbitrarily large.
* **The switch on a row (new id vs. an existing one):** every **non-empty** row carries a switch.
  * **On** — the row brings a **brand new `taskId`** each time the template is applied, copying the row's own title and fields. This is the default.
  * **Off** — every cell built from the row points at **the very `taskId` the row holds**, so they all *mirror* that one task.
  * The switch **toggles both ways**: a template row always has a task behind it, so turning it off never lacks something to point at. *Which* task a row holds is changed in the row's ordinary **Tasks** menu, in Edit Mode, exactly as anywhere else in the tree.
* **A row pointing at an existing task brings that task's own sub-tree**, and the window draws it beneath the row exactly as the tree draws any mirror — because that is all it is. A sub-list belongs to the `taskId`, not to the cell, so the template has no say in what appears under such a row. Pointing a row at an existing task is the ordinary **Tasks** menu in Edit Mode; there is no separate menu for it.
* **When it is applied:** once, at the moment the cell's Edit Mode session ends having **created** a task — never on each keystroke, and never when the session ends up *reusing* an existing task (that task's sub-tree comes with it). A cell whose sub-list is already populated is never re-seeded. The seeded sub-tree rides the session's single History Unit, so one `Ctrl + Z` takes it back together with the title that pulled it in.
* **A binding this tree cannot honour** — the task was deleted, belongs to another task tree (§6), or would duplicate a task inside the sub-tree (*Filtering*, above) — falls back to creating a new task with the row's title, so the row still appears.
* **Off by default.** With the switch off, new cells are created bare exactly as before; the template is kept either way, and turning it off never touches sub-trees it has already produced.

## 5. Priority assignment
* **priority percentage:** The priority percentage displayed at the right side of a cell is the absolute priority percentage of the `taskId`. It is the sum of the absolute priority percentage of all the cells sharing this `taskId`. The priority percentage of a cell in a list is the priority weight of the cell divided by the sum of the priority weights of this sub-list. Its absolute priority percentage is this fraction multiplied by the absolute priority of the parent cell. If the parent cell is the "root" cell, then its absolute priority percentage is 100%.
* **priority weight window:** 
  * When the user clicks on the absolute priority percentage, a **floating window** opens for that sub-list and appears on the **top layer of all floating windows** (above the calendar and every other window). The window has the **priority weight table on its left**, and a **circular (pie) chart on its right** representing the absolute priority percentages of all the tasks in this sub-list. The table has its rows aligned to the cells of the sub-list. It is a table of input fields that only accepts numbers and comma and has increment and decrement buttons to add or remove 1 to the number (0.1 for the header row). The two buttons are placed one above the other in a vertical column at the right side of the number. The header row shows the weight of each column. The weight of each column can only span from 0 to 1 included, the others from 0 to infinity.
  * The priority weight of each cell is calculated by dividing the cell's value by the column's total sum, and then multiplying that result by the column's absolute weight. The absolute weight of the n-th column is its nominal header weight multiplied by a factor, A, where A is one minus the sum of the absolute weights of all preceding columns. This means that reordering columns changes values dynamically.
  * Right above the header row, handles allow to grab the whole column and drag it to place it somewhere else in the table when the click is released. While the user drags, the column gets a grey background and a vertical blue line appears between two consecutive columns to indicate where the column will be placed when the user releases the click. Right-clicking the handle shows a contextual menu with three options: "Add column to the right", "Reset to default" and "Delete column". By default, there is one column with every field set to 1. Each added column has by default every field set to 0. If there is only one column the "Delete Column" option doesn't appear.
  * The window closes when the user clicks **anywhere else**, and that same click still performs its normal action — e.g. clicking another cell closes the window **and** selects that clicked cell. It also closes if its sub-list disappears or a cell enters Edit Mode.
* **percentage contextual menu:** **Right-clicking** the absolute priority percentage shows a contextual menu of exactly two options — **"relative priority"** and **"priority weights"** — instead of the cell's own "edit / copy / deep copy" menu (which stays reachable by right-clicking anywhere else in the cell). "priority weights" opens the same priority weight window a left-click on the percentage opens; "relative priority" opens the relative priority window below. Like the weight window, only one of the two is open at a time and it closes on a click anywhere else.
* **relative priority window:**
  * It shows an **input field for the relative priority of the task** `t` of the clicked cell, and a **drop-down field selecting which parent task** `t_r` this priority is relative to. By default `t_r` is **root**, which makes the number the absolute priority percentage displayed in the task cell. The drop-down lists all the parents of this specific task cell, from root to closest parent.
  * The relative priority of `t` with respect to `t_r` is the sum, over every occurrence of `t` **under** `t_r`, of the product of the cells' own sub-list percentages along the chain from just under `t_r` down to that occurrence. An occurrence outside `t_r`'s sub-tree does not count.
  * Below, there is **one tree per occurrence of `t` under `t_r`**, listed vertically. Each is a horizontal chain read left to right: the cell sitting directly under `t_r` on the left, expanding rightward through the parents down to the occurrence of `t` itself at the right end. Each cell of the chain shows its title and its percentage within its own sub-list, and carries a **pin** button.
  * When the user changes the priority at the top of the window, all the values below adjust so that they **all equally change** — every cell of every chain has its percentage multiplied by one common factor — **except pinned values**, which hold the percentage they had. A pinned cell holds its percentage even when an unpinned cell of the *same* sub-list moves, so pinning adjusts that cell's own weight rather than freezing it. Where two cells of one sub-list both sit on chains their percentages cannot both grow (they sum to 1), and where a cell is an only child its percentage is 100% whatever its weight; in both cases the factor is chosen so the **typed number is still what the tree ends up holding**.
  * The set of pinned cells is defined **per pair of task id and `t_r`**: pinning a cell here does not pin it when the window is opened for another task, or for the same task against another `t_r`. A **"Clear pins"** button drops the whole set. The pins are user data — persisted and synced to the account's other devices.
* **priority weight:** The priority weights are edited only inside the priority weight window (above), so typing in the task tree is never ambiguous with editing a weight. The priority weight can be 0.

## 6. State Management & Undo/Redo Engine

* **Domain model** (the conceptual entities; how they are realized as the immutable MVI Model is `ARCHITECTURE.md` §1):
  * **Cell:** a position in the tree holding a `taskId` (null when the cell is empty), aware of its parent (for ancestor validation, §1), with an optional child sub-list that exists only once the cell is expanded.
  * **Task:** each `taskId` carries a title, an absolute priority percentage (§5), the period ranges of work done and scheduled (§9), a minimum time (§10), a schedule unit (§13), its child `taskIds`, and the cells that use it (its occurrences, ordered by shortest path).
  * **Title index:** each title string maps to the `taskIds` that share it.
* **Initialization:**
  * *Empty DB:* Task Tree initializes with a "root" key pointing to a "main" task (representing the user's active daily life).
  * *Existing DB:* Loads from local persistence. If the last history unit is an incomplete "Edit Mode" state, it evaluates as a canceled edit (`Escape` behavior).
  * *Real-time sync between apps:* The data that must be shared between the account's apps (§6 authoritative data — the task tree, calendar entries the user authored, reminders, the sleep schedule, alarms, settings, history) is synced **in real time**: a change made on one device appears on the others within seconds, with no button press. Because a live stream only reaches apps that are connected at that moment and cannot replay what it missed, real-time delivery is **backed by** a check whenever an app (re)connects and at every launch — an app that was asleep, offline or closed catches up as soon as it is back, rather than staying silently behind.
  * *Server check (every launch):* Whatever it loaded locally, the app **checks the server for remote changes at startup** — it must never open showing a version older than the account's, and it sends up anything a previous session could not. This holds on an ordinary restart, not just when signing in or switching account. It is best-effort: with no connection the app opens on its local data and retries at the next sync moment. The check matters beyond freshness: it is what keeps a device from ever having to resolve a conflict it could have avoided, and it is the safety net for the one case the merge below cannot help (a device that has never synced has nothing to merge against).
  * *Two apps changed things at the same time:* **both sets of changes are kept.** When an app finds that the account moved on while it was holding changes of its own, it does not pick a winner — it **combines** the two against the version they last agreed on, then shares the combination, so every device ends up with all of it. Rows added on either side all appear; a row one app deleted and the other did not touch stays deleted; two apps changing *different* things about the same task (one renames it, the other raises its minimum time) both take effect. Only when the two changed **the very same thing** must one give way, and then the value already on the server is the one that stands. A deletion racing an edit keeps the edit. The **Undo/Redo history is not combined** — each app keeps its own, because `Ctrl + Z` must undo what *this* user just did, not replay another device's steps. When there is nothing to combine against (an app that has never completed a sync), the app falls back to taking the newer side wholesale, and records what it just agreed on so the next time it can combine properly.
* **History Architecture (Deltas):**
  * Every **user** mutation generates a History Unit containing: the **Exact Timestamp** of the change (wall-clock instant), a **Chrono-ID**, and a **Delta**. The Chrono-ID is **0** by default; it is only non-zero to break ties between two units that carry the *same* timestamp — when one technically happens after another at the same recorded instant, the later one takes the next index (1, 2, …) so simultaneous events still sort deterministically. **All History Units live in one shared timeline.** The *categories* — change in Edition Mode, *manual* change in the calendar, change of selection state, **window navigation** (§7), and the rest — are simply how the timeline is **queried and grouped for display and for undo/redo**: each category has its own pointer that walks only its own units. The oldest History Units are removed when a category's length is over 1000. An automatic schedule (§9) is **not** a History Unit — it is fully derived from the current task tree / calendar state, so it carries no undo entry; undo/redo walk only the user changes and the schedule re-derives from whatever state they land on.
  * **Recorded change types:** each unit captures one concrete user change — a change to a list of child `taskIds`, a selection change, an expansion toggle, a task-title change, a priority-weight column move, a priority-weight value change, a manual calendar-record edit, and so on. (The reversible delta encoding that makes each unit both undoable and redoable is the engine's concern — see `ARCHITECTURE.md` §5.)
* **Undo / Redo:**
  * **Undo:** The history pointer decrements. The Delta is applied to the state, and the Delta *inside the unit* is mathematically inverted to represent the forward-change (Redo). `Ctrl + Z` / `Ctrl + Y` walk the history units that are **changes in the currently focused window** (the task tree's edits, or the focused floating window's changes — e.g. the calendar's when it is focused). `Alt + Left` / `Alt + Right` walk the **selection-state** changes (only in the task tree). **Window-navigation units (§7) are recorded but are not walked by any undo/redo command** — focus is not undoable.
  * **Branching:** If an Undo is performed followed by a *new* mutation, all forward (Redo) history units are orphaned/discarded.
* **History Manager:** A floating, draggable in-app window (opened from the lateral menu, like the calendar / reminders windows) **shows all the history unit lists** — it **queries the single history timeline and groups it by category** into columns (the rest, calendar, edit mode, selection, **window navigation**) that sit **side by side with their heads aligned at the top**, each column listing its history units **newest-first (last at the top, first at the bottom)** with the `applied / total` count and the current history-pointer position marked. Each history unit is shown as **a single row** (its short label). **Clicking a row opens an information window** — a modal overlay (dismissed by clicking outside it or its ✕) that shows **all of that unit's own data**: its label, chrono id, and one line per concrete change it carries (renamed / added / removed cells, changed weights or task fields, added / removed / modified calendar blocks with their times, the selection before→after, …). It shows nothing list- or pointer-derived (a unit does not know its own position, category, or applied/current status — those belong to the history list, which renders them in the row, not in the unit's window). An automatic schedule (§9) is **not** a history unit — it is derived from the current state, so it never appears here. Undone units (ahead of the pointer, still redoable) are dimmed. It is read-only — a live view of what undo/redo will walk.
* **Persistence:** **The whole state of the app is persisted** and survives a restart — the tree, occurrences, selection, plus the app-shell state: the **floating windows' positions**, the **app window size**, **which window is in which layer**, and **which window is focused** (§7). **The Undo/Redo history is persisted too** (each category capped at its most recent 1000 units), so a reloaded session keeps its undo/redo timeline; any units committed under the diverged debug clock (§16) are reverted and dropped at the next app start. (Load-once, in-memory truth, debounced write-back — the persistence mechanism is `ARCHITECTURE.md` §4.)

## 7. Lateral menu
* **Page Navigation:** The page navigation button that is persistent through all feature pages is the first element of the left side menu (the button is at the same place in all feature pages but not necessarily in a lateral menu).
* **Window stacking & focus:** The floating windows (calendar, reminders, history, …) overlap the tree. A window is raised to the top of the layers when it is opened and whenever the user presses anywhere inside it. They open in a staggered **cascade** (slightly offset from each other) so a window behind another is never fully hidden and always has a region to click on to bring it forward. (The modal calendar edit window stays above all of them while open.) The **focused** surface is the **top-layer floating window, except when the task tree is focused** (clicking into the tree returns focus to it). The task tree and every floating window are the **focus targets** the user navigates between, and the whole window layout (positions, layers, focus, app size) is persisted (§6).
* **Window navigation:** Switching focus from one window to another is itself recorded as a **History Unit** (the "window navigation" category, §6) — saved for the History Manager but not undoable. **Focusing a floating window makes the task-tree selection disappear and forcibly exits tree Edit Mode** (PRD §4 "Forced Exit"), and **switching to another window leaves Edit Mode in any window** (the calendar edit / add-reminder surfaces close, an open reminder-title field defocuses, etc.). Returning focus to the task tree (clicking into it) does not clear anything.
* **Menu button on an open window:** Clicking a window's lateral-menu button (calendar / reminders / history) when its window is **already shown but not focused** (behind another window) brings it to focus (raises it to the top) rather than closing it. Clicking the button of the **focused** (front) window closes that window. Clicking the button of a **closed** window opens it (and focuses it).
* **Close-windows button:** While **any** floating window is open, a **"✕ Close windows"** button appears near the top of the lateral menu (and disappears again once none are open). Clicking it **closes every floating window at once** (calendar, reminders, history, sleep §17, alarms §18, keyboard shortcuts).
* **Calendar:** A button allows to toggle the display of the calendar in a floating window over the tree (not over the left side menu).
* **Automatic Schedule Switch:** If the switch is set to off, the triggered events to update the schedule (section 9) wait for when the switch is set to on. On by default, and persists between sessions.
* **Look away now:** A **"Look away now"** button takes the 20-second look-away (§15) immediately. It is **always present** in the menu — looking away is something the user may decide to do at any moment, so the button is never hidden, whatever the break cadence currently shows. (The "Look-away voice" toggle right above it is §15's spoken-cue switch.)
  * **It has a system-wide keyboard shortcut, `Ctrl+Shift+Alt+E`, which works while the app is not focused** — for the same reason the away shortcut does: the eyes the break is for are on some other application's window, and a chord that needed OmniApp in front would only ever be pressed when the button is already at hand. Each press takes a fresh 20 s, superseding any look-away still sounding or pending. Desktop only, and best-effort, exactly like the away chord below.
* **Switch task:** A **"Switch task"** button refuses the task the now-line is sitting on: from that instant the schedule must start a **different** task. Like "Look away now" it is always present — realising you want off the current task is something that happens at any moment — and a press while the now-line is on no task at all (a screen break, an inactivity period, an empty stretch) does nothing. The refusal costs the refused task nothing: it keeps its priority and its accumulated share, so it is an ordinary candidate again from the very next slot, and where it is the *only* task that may run at all it simply keeps running rather than the time being left empty. It stands until the schedule has actually started something else, so a re-plan in between (a rule change, the hourly staleness refresh) does not quietly hand the same task back.
  * **It has a system-wide keyboard shortcut, `Ctrl+Shift+Alt+Z`, which works while the app is not focused** — the same reason as the two below: the user is inside the application they are working in when they decide they should be doing something else, and the §11 "task to do now" notification tells them what the schedule switched to. Desktop only, and best-effort, like the other two chords.
* **I'm away:** An **"I'm away"** button declares that the user has left **this device**, overriding the platform's own screen sensor: the device's active session is closed there and then, exactly as a real walk-away would close it, so the pause derives and the presence heartbeat stops. Pressing it again ("I'm back") reopens the session. Per-device, unlike the account-wide Sleep/Work toggle, and purely local runtime state — a restart returns the device to active.
  * **It has a system-wide keyboard shortcut, `Ctrl+Shift+Alt+A`, which works while the app is not focused.** That is the point of it: the moment the button is wanted is the moment the user is leaving the machine and is looking at some other application, so a shortcut that only worked with OmniApp in front would cover the one case where the button itself is already at hand. The shortcut **toggles** — the same press declares "away" and, on the user's return, "back". Desktop only (a phone has no chord to strike, §15's activity signal there is the foreground lease), and best-effort: where the chord is already owned by another application the app runs on without it and the button still works.
* **The system-wide chords are the app's ALONE while it holds them.** `Ctrl+Shift+Alt+A` is also a shortcut inside other applications — Google Docs opens its comments pane on it — and one press that fires two unrelated actions is worse than no chord at all. So the app claims each chord **first come, first served**: it is intercepted ahead of everything else on the machine and **consumed**, and the application in front never receives the keystroke at all. Where the operating system cannot grant that stronger claim, the app falls back to an ordinary system hot-key (the shortcut still works, but another application watching the keyboard may act on the same press), and where it can grant nothing the chord is simply unavailable. Which of the three is in force is stated in the keyboard-shortcuts window, since "nothing happened" and "something else happened too" are otherwise impossible for the user to tell apart.
* **Reminders Manager:** A button allows to toggle the display of the reminders manager in a floating window over the tree (not over the left side menu).
* **Alarms:** A button allows to toggle the display of the alarms window (§18) in a floating window over the tree (not over the left side menu).
* **All tasks:** A button opens a floating window listing **every task of the task tree, flat**, with a **sorter configuration at the top**. Each row shows the task's title, its **number of occurrences in the tree** (a task assigned to several cells is **one row** whose count says how many cells point at it) and its **absolute priority percentage** — the same percentage that task shows on its rows in the tree. The sorter says **which of those two figures orders the list** and **in which direction** (highest first, top to bottom / lowest first, bottom to top); tasks tying on the figure stay in alphabetical order whichever way the list runs, so flipping the direction never re-shuffles a block sharing one percentage. The list is what the tree's *shape* hides: which pieces of work keep coming back across the whole tree, and which ones actually carry the priority. It is a read-only view — the sorter is a way of looking at the tree, not a fact about it, so it is neither persisted nor synced and records no history unit. A task "deleted" by emptying its cell (§4) is not listed.
* **Default sub-tree:** A button allows to toggle the display of the default-sub-tree window (§4), and **to the left of that button sits a switch indicating whether the default sub-tree policy is currently applied**. The two are independent: the window can be opened to build the template while the switch is off, and the switch can be flipped without opening it. Off by default; persisted and synced.
* **Keyboard shortcuts:** The **last** button of the menu opens a floating window listing **every keyboard shortcut the app answers to**, grouped by the surface that owns it: the system-wide chords first (with the line saying which claim the operating system granted them), then the task tree, Edit Mode, undo/redo, the calendar and the task-tree name field. It is a reference list, not a settings page — nothing in it is editable — and it exists because the two system-wide chords are the only actions in the app with no visible control of their own.

## 8. Calendar
* **Current Week:** The calendar window shows the week with the same style as Google Calendar.
* **Day Selection:** When the calendar is displayed, the lateral menu shows the days in the current month and a way to select other day and navigate to other months. This mirrors what is found in Google Calendar.
* **The two layers:** Over the whole timeline the calendar draws two **layers**, each an oblique-line pattern in its own direction: one saying **no computer was unlocked**, the other (opposite slope) saying **no phone was unlocked**. A layer is not a panel — it patterns the calendar without displacing anything, and it is never selectable or editable.
* **A layer is read from the DEVICE, not from the app.** Behind the now-line each layer comes from that device's own operating-system history of **screen lock/unlock** — or, where the platform exposes no such record, of **sleep/awake**. It is deliberately not the app's own activity reporting, which only says when the app happened to be running and being used. Ahead of the now-line nothing has been observed, so only what the rules *promise* is hatched: the **sleep periods** (§17), the **screen breaks** (§15) and the user's own **no-screen periods**, and those hatch both layers whatever any device's history says.
* **A device that cannot be asked was locked.** If a device's history is unavailable — the app running on a computer for the first time, with nothing known about the user's phone — that device is taken to have been **locked** for the whole past, so its layer is drawn across every displayed day up to the now-line. A device whose history *is* available and shows it was never locked is the opposite answer: nothing is drawn for it.
* **The past is only asked for as far as it is shown.** The device's history is queried for the days the calendar is displaying and no further; scrolling further back asks the device again.
* **A no-screen period is where BOTH layers fall.** No computer unlocked *and* no phone unlocked at the same time **is** a no-screen period; any other time is a **screen period**. That single definition is what §9 places the off-screen tasks in and what §15 counts as a pause that serves a screen break. The user can also **add a no-screen period** from the contextual menu: it is exactly "a period carrying both layers", and the derivation never replaces or overwrites it.
* **Panel taxonomy — real vs. decorative:** The calendar draws two kinds of panels. **Real panels** carry the account's actual timeline: the **task panels** and the **inactivity periods**. **Decorative panels** only add a pattern drawn *over* the real panels, without displacing them: the **screen breaks** (§15) and the **no-screen periods** — as do the two layers above. Every panel shows its title at its top-left, except when there is not enough space for it (the title then shows in the panel's info surface — the hover bubble on desktop, the top of the contextual menu on phone).
* **The info surface is a stack of sections.** The calendar draws its elements over one another — a task inside a sleep period, a screen break over that task, the two layers hatched across all of it — so the info surface (the hover bubble on desktop) names **every** one of them that covers the hovered instant, one section each, including **the layers**. The sections read top to bottom in this order: **task = break > inactivity = sleep > no computer unlocked = no phone unlocked**; the pairs joined by "=" are equal, and keep the order the calendar found them in. **When there is a break, there can't be a task** — a screen break suspends the task's chunk rather than cutting it, so the task panel spans the break, but the user is not on that task during it and it is not named.
* **Inactivity periods are grey, and grey means nothing is scheduled there.** An **inactivity period** is drawn as a plain grey period, and it is the one thing that tells the §9 scheduler to place **nothing at all** — not even a task that needs no screen. Four things are the same period under different names: the ones the user **adds** from the contextual menu; the **sleep periods** (§17), which are inactivity periods labelled "Sleep"; the **20-second look-away** (§15) end to end; and the **closed first minute of a 5-minute screen break** — the last two drawn grey inside the screen break's own blue outline. The rest of a screen break is not grey: a 15-minute pose, and a 5-minute pose past its first minute, are periods **reserved** for the work that needs no screen, not stops.
* **The past is fully accounted for.** Every elapsed stretch is either a **task panel** or a **grey period**: whatever the panels leave uncovered in the past is drawn as a grey band labelled **"Inactivity"**, or **"Sleep"** where a sleep period covers it (§17). A derived band of this kind is display-only — unlike a hand-added inactivity period it cannot be moved or removed. The seam between two adjacent panels is not idle time and draws nothing. Ahead of the now-line nothing is greyed except what the rules already place there (sleep, the breaks' closed heads), since the future is a plan, not a record.
* **The two dimensions stay independent.** Grey says whether anything was *scheduled*; a layer says whether a *device was usable*. A stretch where the user sat at the computer doing nothing scheduled is **grey but not hatched**; a night away from every device is **both**; and a stretch where the OS reports the screen was off while the schedule had planned work is **hatched under a task panel** — the device's record and the plan's assumption disagreeing, which is information rather than a contradiction to hide.
* **Task panels:** The calendar shows the periods the user did a task, using the task record saved in `Task Tree`. The title of the `taskId` of the task panel is written at its top-left, and shows in the info surface (useful if the task panel is too short to display the task title). Task record is not saved in the history state. Two task panels with the same task are automatically merged unless one is pinned and the other not pinned.
* **Contextual menu:** The contextual menu opens with a **right-click** on desktop and a **double click and release** on phone. Opened on a panel that is a **task, a no-screen period, a hand-added inactivity period or a sleep period**, it leads with **"edit"** (and, for a task panel, "Remove") — a task panel's edit opens the calendar edit window, a no-screen period's and a **hand-added inactivity period's** the **period editor** (below), a sleep period's the §17 sleep window; a **derived** grey band is display-only and has no "edit" (there is no panel behind it); a **screen break** has no "edit" (there is no editable object behind it — its cadence and length are fixed, §15); on phone the menu is additionally **headed by the panel's info** (the same content as the desktop hover bubble — desktop shows it on hover instead, so it is not in the menu there). Every menu — on a panel or on empty grid — then offers **"add a task"**, **"add a no-screen period"**, **"add an inactivity period"** and "add reminder" (§14), anchored at the clicked time: the panel menu is a superset of the gap menu.
* **Manual add:** "Add a task" opens the calendar edit window with a "save" button that adds a task at the clicked position in the calendar. By default it is the task with the biggest absolute priority percentage, and first in the alphabetic order if there is a tie, and the spanning time is the minimum time of the task. "Add a no-screen period" and "add an inactivity period" both open the **period editor** — the two periods are the same object under different scheduling rules, so they share one window — pre-filled with an hour from the clicked position: a no-screen period carries **both layers**, an inactivity period is the **grey** one the scheduler leaves empty. **Nothing is placed until "save"**, which is what lets a period be given a span the grid cannot be dragged to.

* **The period editor:** each of the two bounds is given as **a date and a time**, as **"now"** (the moving now-line, resolved when the user saves — not when the window opened), or as **"∞"**: a start of ∞ means the period was always running, an end of ∞ means it never stops. Anything half-typed or backwards leaves "save" disabled. An open bound reads as **"∞"** in the panel's info surface, exactly as a derived band with nothing before it does (§12). The everyday case the ∞ start exists for is **an inactivity period from ∞ to now**: it declares that nothing scheduled happened in the whole recorded past, and so clears it (see the override rule below). A period stays editable/movable like any panel afterwards, and moving or resizing one re-applies its rules over its new span.
* **Automatic override on add:** When the user adds an **on-screen task over a no-screen period**, the app automatically overrides the no-screen period — it is **deleted or trimmed** so the new screen task fits — and vice versa: adding/extending a **no-screen period over on-screen task panels** deletes or trims them to fit. The user's explicit placement always wins over the panel it lands on. An **inactivity period is grey, and grey refuses everybody** (§9), so it overrides **every** task panel it covers — the off-screen ones too, which a no-screen period leaves alone — and every task panel overrides it in turn.
* **A period also clears the WORK RECORDED under it.** The elapsed part of a period the user lays (or drags onto the past) is a statement about what did *not* happen there, so the task record inside it goes the same way the panels do — a no-screen period drops the **on-screen** tasks' records (an off-screen task is allowed to run in one, §9, so its record over one is true), a grey inactivity period drops **every** task's. This is the same rule §9 applies as work is banked, applied at once instead of at the next start-up. Like every other change to the record it is not an Undo/Redo step: undoing the period restores the panels it trimmed, not the records it cleared.
* **Phone interactions:** Where desktop uses the mouse, the phone maps: **move a panel** — desktop drags it directly, phone uses the **"move"** option of the contextual menu; **panel info** — desktop shows a hover bubble, phone shows it at the top of the contextual menu; **contextual menu** — right-click vs. double click and release; **zoom** — see below.
* **calendar edit window:** The "Edit" option opens a floating window over the calendar floating window and the task tree. This window has an input field that is similar to the cells in `Change Task` mode in the tree task: same Edit Mode with the task menu and title suggestion menu, including the same default selection (the first task of the task menu, not "New task"). Unlike in the task tree, the title suggestion menu and the task suggestion menu only suggest tasks that don't have child tasks. Creating a new task in the calendar doesn't create one in the task tree. There are two input fields for the beginning time and the ending time. Below them are four independent **pin switches** controlling how the panel is held when the calendar reschedules: **Existence** (keep this occurrence — on by default for a new panel), **Position** (fix where it sits, confined to a position granularity), **Spanning** (fix its duration), and **Distance** (fix the gap to a reference occurrence). Each switch constrains how the §9 scheduler may move the panel when it regenerates the surrounding schedule. Below the pin switches sit two **task-level screen switches** (stored on the task, so they apply to every occurrence; hidden for a calendar-only "New task", which has no task object): **"On screen"** — whether the task is done at a screen; an on-screen task may only be placed on screen periods and an off-screen task only on no-screen periods (§9) — and **"Doable during a screen break"** — the task may be scheduled inside a **5- or 15-minute screen break** (§15), after that break's closed first minute; even when on, a task whose minimum time (§10) is longer than what is left of the break is never scheduled there. **A task doable during a screen break must also be one that needs no screen** — a screen break is time away from the screen, so the second switch only appears while "On screen" is **off**, and turning "On screen" back on clears it.
* **Manual drags:** The user can drag a task in the calendar by clicking on it and dragging while still holding the click. When dragging the task over other task periods, there must not be overlaps, so as the mouse come over consecutive tasks, the dragged task stay stick to the end of this group, and as soon as the mouse gets closer to the start of the group than its end, the dragged task appears before the group. When it appears in gaps that are shorter than the dragged task, the dragged task shorten to fit, but remembers its original side for when it appears in wider gaps. The calendar is considered to have changed and the move is saved in a history unit only when the user releases the click.
* **extend or shorten:** The user can also grab the beginning or the end of the task to extend or shorten it. When it is going to overlaps with other tasks, it can't be dragged any further. The mouse gets the standard shape on hover that indicates the user can grab the edge.
* **Overlap Mode:** When the user moves a task panel or drags its ends, pressing `O` toggles the overlap mode where the task panel can overlap with others. When a task overlaps with others, they share the time period horizontally. By default, the task panel that is dragged occupies 1/n of the width, with n the number of task panels in the overlap. Only the newly-dropped panel takes 1/n; the existing panels split the remaining (n-1)/n in their current proportions. Preserves prior manual adjustments. The user can then drag the vertical edges in the overlap to adjust the width occupation of each task panel. When the task panel is partly in an overlapping area, only the overlapped part has the width reduction.
* **undo:** The user can undo and redo (Ctrl + Z and Ctrl + Y) the state of the calendar when the calendar is in focus. Every changes in the calendar is stored at the same place as the other history units. 
* **focus:** When the calendar (or any floating window, §7) is in focus, the task tree doesn't catch letter typing (the main selection doesn't enter Edit Mode); Ctrl+Z/Y then route to the focused window's history.
* **Zoom:** The user can zoom the calendar vertically (the hour-row height scales) with the standard commands while the calendar is in focus. Desktop: `Ctrl` + `+`/`-` zooms in/out (numpad `+`/`-` too), `Ctrl` + `0` resets to the default zoom, and `Ctrl` + mouse scroll zooms (scroll up to zoom in, down to zoom out) instead of scrolling the grid. Phone: **two fingers spreading/closing** (pinch) zooms in/out, and **double tap and drag** zooms too (drag away from the tap to zoom in, back toward it to zoom out). The zoom is **directed at the mouse**: the point in time under the cursor stays under the cursor as the grid scales (for keyboard zoom with the cursor outside the grid, it pivots around the viewport centre). Zoom ranges from a half up to sixteen times the base hour height.
* **Default zoom (awake day):** The **default zoom** fits the **awake part of the day — from wake-up to bed-time (§17)** — into the viewport, scrolled to the wake line, so the whole waking day is visible without manual zooming. **Switching to a different week resets to that week's default**, which can differ between weeks as the wake/bed time drifts (§17). When there is no usable sleep window it falls back to opening at the current time. A manual zoom persists until the week changes.
* **Graduation:** The time graduation gets finer as the user zooms in — the gutter labels and the grid lines step through 60 → 30 → 15 → 10 → 5 (down to 1) minute intervals, picking the finest interval whose ticks are still tall enough to read. Sub-hour lines are drawn fainter than the on-the-hour lines.

## 9. Scheduler
* **Scheduling:** Every time the user changes the calendar in the last 168 hours and the next 168 hours, a hole is automatically added to indicate device sleep, or when the user changes the task tree, if the automatic schedule switch is on then all the not pinned task panels **within the scheduling horizon** (below) are cut and replaced by a new calculated schedule. As soon as the horizon is not filled with automatic schedule, it continues the schedule to fill it. Two consecutive task panels with the same task merge. An automatic schedule is **not** saved in a History Unit (§6): it is derived from the current state, so it is never recorded and never undone on its own — the user's change that triggered it is the only history unit, and the schedule re-derives after any undo/redo. At app start there is **no** History Unit; e.g. a 15-minute pause alone adds none, while selecting a cell and typing "y" to create a schedule produces exactly two (one selection, one Edition-Mode change) and the resulting schedule adds none.
* **Scheduling horizon — it follows the week displayed:** The schedule is materialized only out to **the end of the week the calendar is currently showing** — never systematically 168 hours ahead. Staying on the current week therefore computes that week and **no later day**; opening a further week extends the horizon to it. With **no calendar open** the horizon shrinks to **24 hours**, which is all the notifications (§11/§13), the wind-down and break cues (§15) and the schedule-unit deadlines (§10) need while nothing is on screen. The horizon is capped at **168 hours**: a week beyond that is never materialized into the app's stored schedule (see the next point).
* **A far week is computed asynchronously, and never kept:** Because a day's schedule depends on every day before it, selecting a week beyond the 168-hour cap requires calculating the schedule of every day from now out to that week. That calculation **must never freeze the calendar**: it runs off the UI thread while the window stays fully interactive, with a **"Calculating…"** hint in the header until it is ready. Its result is **display-only** — it is not stored, so navigating back to a near week simply shows the ordinary schedule again and the far calculation is discarded rather than accumulated in memory. (Consequence: while sitting on such a far week, an edit made elsewhere does not refresh it until the user navigates away and back.)
* **task choice — the cyclic proportional-share model (`side-dev/README.md`, reference implementation `side-dev/test.py`):** Each task carries a **virtual clock** — the time it has been served divided by its priority percentage. The scheduler always places the task with the **smallest** virtual clock (the most starved one) and gives it just enough time to catch up with the runner-up, never less than its minimum time. This satisfies the target percentages **at the smallest scale the minimum times allow** — two 50 % tasks with a 10-minute minimum alternate every 10 minutes, not every hour. A task panel can never have a spanning time shorter than the minimum time of the task — a gap too short for any minimum is left **empty** rather than filled with a sliver — and once a task is placed nothing else may be placed until that minimum has elapsed. A task is never placed twice in a row: a task that is owed a lot gets a *denser* presence, not one long block.
* **The timeline is a list of periods, each accepting a set of tasks; the plan is a finite list of rules.** Because the timeline is infinite, the schedule is not a list of slots but a **prefix played once followed by a cycle repeated forever** — so drawing any span is just unrolling that list, and any instant can be looked up directly. The cycle is built analytically on the smallest period that can exist, `T = max(minimum ÷ priority)`, where each task's budget `priority × T` is at least its minimum, so the shares inside the cycle are **exact**. The prefix is everything up to the point where nothing is left to disturb the schedule: pre-placed blocks, restricted periods, and the tail of the influence field below. To keep the rule list manageable there is a strict maximum number of rules; past it the cycle falls back to one block per task (same period, same exact shares, coarsest interleaving), and if even the prefix fills the budget the cycle is dropped and the timeline is left truncated.
* **The influence field — how a deprived task is compensated, and why the compensation is bounded:** A task can be deprived of the timeline in exactly two ways, and they are the same event: a **fixed block owned by another task** hands that task a lump of timeline nobody else gets, and a **period that does not accept a task** forbids it outright. Both are one object — an **exclusion**. Around an exclusion the schedule is deliberately distorted in favour of the deprived task, and the distortion **decays exponentially with the distance**, the same ramp before the exclusion and after it. The distortion is **capped**, so near an exclusion a task dominates its neighbourhood but never owns it: an exclusion ten times longer buys a few times more compensation, not ten times more (logarithmic, not proportional). It also vanishes at a finite distance, so the schedule returns to its steady cycle. Consecutive or overlapping exclusions count as one — ten short bans in a row are one long ban, not ten small ones — and an interval that excludes **everybody** (maintenance, a holiday, a window that allows nothing) takes the same amount from everyone, creates no relative distortion, and is ignored. The compensated time is a genuinely higher local share and is never clawed back later; symmetrically an imbalance larger than one period is forgotten exponentially, so an enormous block — or a very long ban — is repaid up to that same logarithmic bound rather than hour for hour.
* **The scheduler runs only on a change to its inputs:** The schedule is a **function of time** — it is calculated when, and only when, the user (or another device's user, through a sync pull) changes something the calculation depends on: the task tree and its priorities, a minimum time, a screen switch, a pinned/manual calendar block, a no-screen or inactivity period, the sleep schedule, the screen-break configuration, or the automatic-schedule switch. Those changes are **debounced** (a burst of edits costs one calculation). Time passing is **not** such a change: the now-line advancing only consumes the plan already calculated, and reaching further out (the rolling horizon, or navigating the calendar to a further week) **continues** the existing schedule to fill the horizon rather than re-planning what is already on screen.
* **Screen placement — every restriction is a period, and nothing else:** The whole of OmniApp's world reaches the scheduler as the reference model's one input: *the timeline is a list of periods, each defining the set of tasks it accepts*. There is no second mechanism.
  - an **inactivity period** — the grey one (§8): a hand-added one, or a **sleep period** (§17) — accepts **no task at all**, not even one that needs no screen. Grey means the scheduler places nothing there.
  - a **no-screen period** — the stretch where both layers fall (§8) — accepts only the tasks that **need no screen**; everywhere else accepts only the tasks that **do**.
  - the **20-second look-away** accepts **no task at all** (it is an inactivity period too, §8).
  - a **5- or 15-minute screen break** accepts, **only after its first minute**, the tasks that need no screen and are marked **doable during a screen break** (§8) — the first minute is the time the user needs to actually get off the screen, and accepts nobody. A break shorter than that minute (a debug-retimed one, §16) is closed end to end.

  Two consequences fall straight out of the model rather than being special cases: a task is a candidate only while its **minimum time (§10) fits** what is left of the period, so it is never scheduled in a break too short for it; and a period that accepts **nobody** excludes everybody equally, so it creates **no influence field** — which is why the look-away, recurring every 20 minutes forever, does not distort the plan around each of its occurrences, while a pose's open tail (which hands the break-doable tasks time nobody else gets) legitimately does.
* **Live update while still at a screen:** If devices are still reporting activity (fresh presence beats, §15) when a screen break was scheduled to start, the break is **not** marked missed: its drawn occurrence **slides forward on the now-line** (§15 now-line clamp) and the calendar re-projects the break markers continuously as it slides. What does **not** happen is a re-plan: the sliding break is a consequence of time passing, not a change to the scheduling rules, so the surrounding **task panels stay where they are** until the next rule change refills them. (Earlier revisions of this bullet said "the downstream fill re-flows" and keyed the signal on open WebSocket connections; both are obsolete — the per-tick refill was removed because it churned the whole work plan continuously while the user was away, and the activity signal is now the presence heartbeat.)
* **Past no-screen ⇒ past inactivity:** When a **no-screen period** turns out to have covered a time where a task was scheduled, the app must **not assume anything** about the task having been done: no task record is banked for that stretch — it is set as a **past inactivity period** (a real grey panel, §8) and the surrounding task panel is trimmed around it. This is the one place an inactivity period is created automatically, and it is about a task that *was* scheduled; an idle stretch where nothing was scheduled produces no panel at all (§8).
* **Tie-breaker:** Equal virtual clocks break by higher priority, then alphabetically by title — so a first calculation on a level playing field is deterministic. (A second tie-breaker once specified here — "choose the timeline with the biggest amount of task panels" — was dropped: the fill is a single deterministic greedy walk and never enumerates alternative timelines, so there was no set of candidates for such a rule to choose between.)
* **Example 1 (the influence field, seen from the calendar):**
  - tasks: A (50%, 45min), B (50%, 45min)
  - pinned panels: lots of A before t_now
  - result: **B first, for a bounded catch-up, then A, B, A, …** "Lots of A" (say 17 hours) is, for B, a 17-hour exclusion ending at the now-line, so B opens on the compensation ramp — the reference implementation hands it about 4½ hours and then returns to alternating. It does **not** buy B 17 hours of catch-up, and it does not merely reorder the first pick either: two earlier revisions of this document said the deficit was not balanced at all, then that it was balanced up to one full rotation `C = Σ minimum times` with the excess decaying at a fixed half-life. `side-dev/README.md` replaces both with the exclusion field above — the compensation is logarithmic in the length of the deprivation and decays with the distance to it.

## 10. Minimum time for a task
* **Definition:** Every task has a minimum time defined. It is 45 minutes by default.
* **New Task:** The spanning time of the new task is the minimum time associated to the task, minus the accumulated spanning time of this same task recorded in the past if separated by less than 10 minutes between each session. If the result is negative, then the new task gets the minimum time associated to the task. The task panel must be reduced to avoid overlapping with pinned task panels. In the §9 fill this credit applies only to the **first** allocation of a plan (the only one that can have an effort still running behind it) and only when the scheduler was not already giving the task *more* than its minimum — a catch-up must never be shortened; from there on the virtual clocks are what keep a just-served task from being served again.
* **Display:** The minimum time of the task is shown at the right side of the priority weight display. When the user clicks on it, it behaves similarly to the absolute priority display. It becomes an input field with increment and decrement arrows on its right side. When selecting other cells, it gets back to a simple display (keeping the typed value). While in input field mode, typing won't enter Edit Mode, and the left/right/Home/End keys, Backspace/Delete and the field's own copy/paste act on the field's text. Enter, Tab and Escape act the same as in a cell's Edit Mode: **Enter** moves the selection down to the next cell, **Shift+Enter** and **Shift+Tab** move up, **Tab** moves into the first child (expanding it if needed), and **Escape** abandons the edit, restoring the minimum time to its value when the field was opened.

## 12. Device sleep
* **When The Device Wakes Up:** The app checks the time periods where the device was sleeping, which means the user wasn't doing the scheduled task during those periods. The task panel on the calendar then gets the holes corresponding to the sleeping periods.
* **Relation to no-screen periods (§8/§15):** A device sleep is one source of evidence for an account-wide **no-screen period** (the general signal is the account's activity reporting stopping, §15). Per §9, the app assumes nothing about work scheduled under a past no-screen window: the hole cut out of the task panel is a **past inactivity period**, and no task record is banked over it.

## 13. Schedule Unit
* **Schedule:** A task can have an sequential list of objects containing a title and a spanning time.
* **Notification:** If the task has a schedule unit, then the notification that tells the user to switch to this task must also tell him the deadlines of each elements of the schedule unit.
* **Cell Contextual Menu:** Right-clicking a populated cell in the task tree shows a contextual menu with **"start this task now"** (on a schedulable leaf), **"edit"**, **"copy"**, **"deep copy"** and — when a default sub-tree (§7) has been defined — **"add default sub-tree"**. Empty cells and the root/main cell have no contextual menu. Like "copy", these act on the whole block when the right-click lands inside a multi-selection — "start this task now" excepted, which names one task however many cells are selected.
  * **"start this task now"** asks the schedule to put **this** task at the now-line: from that instant the plan starts it, whatever it would otherwise have chosen. It is the mirror image of §7's "Switch task" button, which refuses the task the now-line is on, and it costs the task nothing either way — it is charged for the time exactly as if the scheduler had picked it, so only the **first** slot is the user's answer and everything after it is the ordinary schedule. It is offered only on a task the scheduler actually places: a task with children is a grouping (§9 picks the leaves), so there is nothing to start. The request stands until the schedule has genuinely moved on to another task, so a re-plan in between (a rule change, the hourly staleness refresh) does not quietly take the user off the task they asked for; where the current period will not have that task at all (a screen break, a no-screen period the task may not run in) it simply loses the slot, as it would have anyway.
  * **"add default sub-tree"** applies the §7 template on demand, whether or not the default-sub-tree switch is on and whether or not the task is new. It applies to the **leaves** of the cell's sub-tree — a cell with an empty sub-tree gets it directly; a cell that is already broken down gets it under each of the tasks below it that have an empty sub-tree. One undoable step; every cell walked is expanded.
* **Edition Window ("edit"):** "edit" opens a floating pop-up window with **three sections**, over a dimming scrim that dismisses it. At the bottom right, a Cancel and a Save button; Save writes all three sections at once, and only the sections the user actually changed become History Units (§6), so saving an untouched window records nothing.
  * **Section 1 — the screen switch:** a switch defining whether the task **can be done during a no-screen period**. On means the task is done away from a screen, so §9 may only place it inside a no-screen period; off (the default) means it is screen work.
  * **Section 2 — the schedule unit:** the list shown vertically. The titles are input fields and the spanning times are also input fields but with increment and decrement buttons. At the right of a pair, a bin button (to remove the pair) and a plus button (to insert a pair above). At the end of the list, a single plus button. If the sum of the spanning times is higher than the minimum time of the task, the Save button is not clickable.
  * **Section 3 — the text:** a free-form, multi-line text document associated with the task id (shared across every cell pointing at that task). Empty until the user writes something.
  * **Leaf tasks only for the first two sections:** a task with a **child task** is never placed by the scheduler (§9 picks the leaves), so its screen switch and schedule unit would have no effect — a parent cell's edit window therefore shows the **text section alone**.
* **What the two copies act on:** right-clicking a cell that is **part of the current multi-selection** copies the **whole selected block** — the same block §4's Ctrl+C takes, so the menu and the chord never disagree. A right-click on a cell outside the selection copies that cell alone.
* **Copy ("copy"):** writes the task(s) **alone** to the clipboard — one level, no children: its title, its priority-weight row, its minimum time (§10) and everything the edit window holds (the screen switch, the schedule unit, the text). It is the same readable text §4's Ctrl+C produces (which takes the whole sub-tree instead of the cell alone), so **Ctrl+V pastes it back** with all of those restored; a payload written before this format existed still pastes, with the fields it says nothing about left at their defaults.
* **Deep copy ("deep copy"):** the same, **with the tasks under them** — but it asks how far down first, in a floating window over the same dimming scrim:
  * a **maximum depth** input with increment and decrement buttons, a copied cell itself counting as the first level;
  * below it, **one path** down to the deepest level that depth reaches — the deepest branch under whichever copied cell reaches furthest, cut to that many levels — so the number reads as a real place in the tree. Raising the depth extends that path rather than switching it to another branch. When the path is too long for the window it is shown on **one scrolled line held at its deep end**: the parent part is hidden off to the **left**, and a **horizontal scrollbar** under the line lets the user see it all;
  * three **switches** saying what each copied task carries, all three on by default:
    * **copy the task ids** — off, the text names no task, so pasting it always creates **new** tasks (and, §7, seeds the default sub-tree under the leaves it mints) instead of coming back as the tasks it was copied from;
    * **copy the priority weight tables** — off, each sub-list's weight table (its column header and the cells' value rows) is replaced by the single number it produces: the task's **priority percentage within its own sub-list**. Pasting that back reproduces those percentages, as one weight column holding them;
    * **copy the task text** — off, the §13 text section is left behind; everything else the edit window holds still travels.
  * **Enter** or the **copy** button makes the copy and leaves the window; **reset** puts the maximum depth back to **20**, its default value, and turns all three switches back on; **Cancel** or a click on the scrim dismisses it without copying.
  * The maximum depth **and the three switches are one answer for the whole account**, not for this copy: the window opens on them and copying writes them back, so the menu's "copy" and §4's Ctrl+C / Ctrl+X carry whatever the window was last told (the depth alone excepted — the chord always takes the whole sub-tree). Cancelling changes none of them.

## 14. Reminders
* **Window:** The reminders manager is a floating window holding a vertical list of rows; each row is a title, a recurrence and a time of day. The recurrence is a number input with a **unit dropdown** at its right. Interval units — **days** (default), **months** (every `n × 365.24219 / 12` days) or **years** (every `n × 365.24219` days) — and rate units — **per week** (`n` times a week → every `7 ÷ n` days), **per month** (`n` times a month → every `365.24219 / 12 ÷ n` days) or **per year** (`n` times a year → every `365.24219 ÷ n` days). Months/years use the mean Gregorian year length. The number accepts a **formula** (an arithmetic expression — `+ - * /`, parentheses, decimals — e.g. `31/21`) as well as a plain number; the field keeps the raw formula and the chosen unit so they round-trip, while the cadence in days is the evaluated number times the unit. When the field holds a formula, its evaluated result is shown just to the right of the field, rounded to two decimals with a comma separator (e.g. `30/21` → `=1,43`). The result is read as: **≥ 1** is a day cadence (`2` = alternate days; `31/21` ≈ 21 days out of every 31); **between 0 and 1** is **every day**; **≤ 0 or blank** is a **one-off** placed today only (so a title alone makes a single reminder).
* **Title field menus (reminders manager):** Focusing a row's **title input field** is that row's **Edit mode**, mirroring a task cell's Edit Mode (PRD §4) and sharing its structure with the "add a checked reminder" window. Beneath the field it shows a **Mode selector** with two modes — **Change Reminder** and **Rename** (the reminder counterpart of the cell's "Change Task" / "Rename") — followed by a **reminder id menu** ("Reminders", shown in **Change Reminder** mode only) and a **title-suggestion menu** ("Title suggestions", shown in both modes). The menus appear only while the field is focused and **disappear when it loses focus**; the mode resets to **Change Reminder** whenever focus moves to a different row. **Clicking anywhere in the reminders window other than the focused title field or its edit-mode menus leaves Edit mode** (the click clears the field's focus, hiding the menus). Picking an item **keeps the field focused** (menus stay active, like a task cell after a pick). The id menu lists reminders whose title matches what's typed that are **not already a row in this window** — i.e. reminders that exist only as "add a checked reminder" panels on the calendar (a reminder created that way is *not* automatically a manager row; it becomes one once a row adopts it here). The menu never re-suggests a reminder a row already represents: each **other** row excludes the id it resolves to, and the **focused** row excludes its **own** id. Excluding the focused row's own id also hides its provisional **"New Reminder"** identity — that freshly-minted id is only persisted (as a chore) while "New Reminder" is selected, so it must not reappear as a selectable entry (as soon as "New Reminder" is unselected the id ceases to exist). **Exception:** when the focused row's own id is **independently referenced by a checked reminder** on the calendar, it is a *real* reminder (it would survive the row detaching), so it **is** shown — the menu then lists both it and any other matching reminder (so a row sharing a title with another reminder shows two entries), and the row's "New Reminder" pick no longer forces the New highlight (the default falls on the first matching reminder). Picking **"New Reminder"** there mints a third reminder and leaves the previous id alive on its checked tag. The reminder the focused row merely **adopts by default** is *not* excluded (it always has a different id, since minted ids dodge every known reminder id): it stays in the menu, selected by default, so the user can confirm the reuse or pick "New Reminder" instead — otherwise selecting a matching title would leave the menu empty and hidden. Mirroring the task cell's Tasks menu (shown only beyond "New task"), the id menu is **hidden unless at least one such reminder matches**, and when shown always leads with a **"New Reminder"** row. **Default selection:** the **first reminder id that is not already in this window** is selected by default; when there are none, **"New Reminder"** is selected. *Action:* a row **resolves** its reminder id from its title like the "add a checked reminder" window — a row still being created (not already an existing reminder) **adopts by default** the title-matching reminder selected above (the row becomes that reminder), so relying on the default selection is enough and no explicit pick is needed. Explicitly choosing **"New Reminder"** keeps the row's own freshly-minted id even when its title matches (re-resolving from the title again once the title is edited), and explicitly picking a different reminder adopts that one instead. The **Rename** mode hides the id menu so the title is edited in place.
* **Calendar tags:** A reminder is *not* a task panel and has no spanning time: it shows on the calendar as a checkable tag (a zero-duration marker) placed at its time of day — or at the **current time** when the time-of-day field is left blank — recurring per the rule above. The reminder flags are calculated for the **whole focused week** — from the current time to the end of the week the calendar is showing — so navigating to a week shows that week's reminders; each tag's checked state is carried over from the persisted reminders. The calendar updates each time the reminders manager window changes. For a cadence ≥ 1 the value is accumulated at each iteration and for every iteration the closest integer indicates the chosen day (so a fractional cadence hits its exact count over the smallest whole-number window without drifting); if there were no iterations before or too far in the past, the accumulated counter starts from today. Because a reminder has no spanning time it is **not** an obstacle to the task scheduler (§9) — unlike the panels it replaces it never blocks, reshapes, or is avoided by the auto schedule. Reminder tags scheduled at the same time — or close enough that their fixed-height tags would overlap — **stack downward** below one another (each pushed under the previous), rather than sharing the column width; the now-line overdue stack behaves the same way.
* **Display switch (calendar window):** a switch in the calendar window toggles whether the reminder tags are **drawn**. When off, no reminder tags are shown. This is a purely **cosmetic** calendar choice — the underlying chores and their scheduling/checked state are unchanged. The switch state persists across sessions.
* **Checking off:** The user can check a reminder once it is done. Checking (and un-checking) a reminder is saved in a History Unit (undoable, §6). A **checked** reminder tag is a completion record keyed by the reminder's **stable id** (not the row's position), so its checked state survives a regeneration when the reminders manager changes, and also survives the row being **reordered, removed, or detached** to a different reminder — the completion keeps pointing at the original reminder. (It is not reset, mirroring the old pin behaviour.)
* **Reference counting / garbage collection:** A reminder id exists only while it is **referenced** — by a row in the reminders window, or by a checked reminder on the calendar. An id referenced by neither is **deleted** (its leftover unchecked tags are dropped on the next regeneration); this mirrors the task tree, where a `taskId` with no cell pointing at it is purged (§4). So removing a row that was never checked deletes its reminder, while removing/detaching a row that *was* checked leaves the reminder alive on its checked tag (still selectable in the id menu).
* **Accumulation when missed:** A reminder that has not been checked by its scheduled time becomes overdue: it leaves its scheduled slot and accumulates on the now-line (the line that marks the current time on the calendar). Several overdue reminders stack on the now-line. An overdue reminder remains on the now-line until the user checks it off (which marks it done and is the History Unit above).
* **Reminder identity:** Every reminder has a stable **id** (like a task's id) in addition to its (editable) title, so a reminder can be referenced independently of its title.
* **Constrained in:** Each reminder row has a **"constrained in"** button at its right; clicking it opens a floating window with a single reminder-name **input field** carrying the same **title-suggestion** and **reminder id** menus as the manager (no Mode selector — there is nothing to rename), and **Cancel** / **Save** buttons at the bottom-right. Picking / typing an existing reminder there constrains this reminder to it; the chosen reminder's **name is then shown to the right of the "constrained in" button** (with a small ✕ to detach). A **constrained** reminder is only ever placed on the days its constraining reminder also occurs, while still **averaging its own cadence** — e.g. "cyclopirox" at *2.5 per week* constrained to "shampoo" *every 3 days* appears about 2.5 times a week but only on shampoo days. (When its cadence is shorter than the constraint's it lands on every constraining day, capped at that rate.) A reminder cannot be constrained to itself; a blank, dangling (target removed) or cyclic constraint falls back to the reminder's own unconstrained cadence.
* **Add reminder:** Right-clicking anywhere on the calendar offers, alongside "add a task", the option **"add reminder"**. It opens a floating window with a **title input field** that shows the same **Edit-mode** menu block as the reminders manager, **except that the Mode selector does not appear** — this window is always in **Change Reminder** mode. Beneath the field it shows a **reminder id menu** ("Reminders") with a leading **"New Reminder"** row (record against a brand-new, distinct reminder) followed by existing reminders, and a **title-suggestion menu** — a **time input field on its right** pre-filled with the time of day at the right-clicked position — and two switches, **checked** and **pinned** (checked defaults on). The id menu defaults to the existing reminder whose title matches what's typed (so the tag feeds that reminder), or to **"New Reminder"** when nothing matches; picking an existing reminder attaches the tag to that reminder's id, while picking "New Reminder" forces a new distinct reminder even when the title matches an existing one. **Cancel** and **Save** buttons sit at the bottom-right. Saving places a reminder tag for the chosen id at that time with the chosen switches (recorded as a History Unit). A **checked** tag is a completion: it is kept across reminder regeneration and feeds the reminder schedule (reminders are scheduled like tasks — satisfying the target dispersion at the smallest level possible, with past reminders acting as tie-breakers). A **pinned** tag is a placement that survives regeneration even when not checked (e.g. a manually placed future or overdue reminder). A tag that is **neither checked nor pinned** has no reference and is dropped on the next regeneration (it would otherwise be a stray, like an orphaned generated tag). A reminder id stays a live, selectable identity while it has a row, a checked tag, **or** a pinned tag.

## 15. Screen breaks
* **Definition:** Screen breaks (formerly "side tasks") are for **eye health care**. They are placed on the calendar with a **real spanning time** (unlike reminders §14, which have none), materialized like a task panel showing their title. As calendar panels they are **decorative** (§8 taxonomy): a pattern drawn over the real panels, while the §9 fill still leaves an exact gap for them.
* **Account-wide pauses & the derived no-screen periods:** A **pause** is any window when **no app signed in to the account reported activity to the server**. That report is a **presence heartbeat row**, not a socket (`ARCHITECTURE.md` §8 — the presence WebSocket was retired): a device beats only while genuinely in use — the desktop while the app runs signed-in with an interactive, unlocked screen; the phone only while **unlocked and in the foreground** (its foreground service listens to the lock/unlock events and starts/stops the beat accordingly, and a clean screen-off is reported immediately instead of being waited out). All the apps sync their local DB with the remote one, and each gets the derived **no-screen periods** — the complement of the union of every device's activity windows over the last 168 hours — drawn as decorative no-screen panels (§8 taxonomy) and folded into the break seeding below. The **manually added no-screen periods** (§8) are the user's own data: the derivation never replaces or overwrites them. The derived periods are **carved around the nightly Sleep windows** (§17) so a night reads as "Sleep", not "no screen". A pause is judged account-wide: one device's silence is not a pause if another device was still active. **No-screen is the default: a window is a pause unless some device actually reported activity over it.** (Requires cross-device sync signed in, else the calendar falls back to this device's own activity history.)
* **Driven by the no-screen history:** Each screen break is due based on whether the user has actually taken its pause, which the account's no-screen history shows (a **no-screen period** — an account-wide window with no reported activity, or an OS-recorded device sleep where the platform exposes a sleep/wake log — of at least the pause's length counts as taking that pause). An **inactivity** period is *not* a pause: it is screen time (§8), so it never serves a break. **After a pause of at least the pause's length, the next occurrence of that pause is one interval later:**
  - after a ≥20-second pause, the next look-away is **20 minutes** later;
  - after a ≥5-minute pause, the next 5-minute pose is **1 hour** later;
  - after a ≥15-minute pause, the next 15-minute pose is **2 hours** later.
* **Projected across the focused week:** The screen breaks are computed from **now to the end of the currently focused week** (in practice, across the scheduling horizon ahead), interleaving the three recurrences forward — not just the single next one. The 20-second look-away recurs an interval after it **starts** (its length is negligible); the 5- and 15-minute poses recur an interval after they **end** (so the 15-minute pose lands every 2 h 15 min start-to-start, the 5-minute pose every 1 h 05 min).
* **Now-line clamp:** **If the current time crosses a screen break before the user has taken the pause, that occurrence's start stays at the current time** (it sticks to the now-line instead of drifting into the past) until the pause is taken; a never-taken pause is therefore due immediately. Equivalently: if the account is **still reporting activity** when a screen break was scheduled to start, the break slides forward rather than being marked missed. The slide is a **display projection** — the break markers are re-projected as the now-line moves, but the task plan around them is **not** re-planned by time passing (§9). When the user takes a pause (a qualifying no-screen period), the clocks of every pause it covers reset and the break projection re-flows. **The cue that fires on a pose is keyed on its fixed due instant `lastRest + interval`, never on the sliding drawn start.**
* **What stays on the calendar once it is past:** only a break the app actually **conducted** — which is only ever the **20-second look-away**. The app announces it, waits the 20 s and says to resume work, so it happened and it stays drawn where it happened. A look-away that **started but did not finish** — the manual "Look away now" below supersedes the one in progress, or the app stops mid-break — is **erased**: nothing about it is kept. The **5- and 15-minute poses draw nothing in the past**: nothing about a pose ever happens in the app, it is only recognized after the fact from a pause, and that pause is already on the calendar as what it really was (the device layers, the no-screen period, the grey "Inactivity" band) — drawing a pose band over it would state the same fact twice and give it the break's nominal length instead of the pause's real one.
* **A pause re-anchors shorter pauses:** taking any pause counts as taking every shorter pause too, so placing a pause restarts each **shorter** pause an interval after it **ends** — the look-away always lands **20 minutes after a pose ends** ("after a ≥20-second pause, the next look-away is 20 minutes later"), and the 5-minute pose lands 1 h after a 15-minute pose ends. A shorter pause therefore never appears within its own interval of a longer pose.
* **Shorter-pause → pose merge:** if a shorter pause comes due **just before** a longer pose such that its window would overlap that pose, the shorter pause is **absorbed** — it **becomes** the longer pose, which starts at the shorter pause's (earlier) start and ends its own length later, and the longer pose's own next occurrence is pushed an interval after the merged pause ends. This applies both to the **5-minute → 15-minute** merge and to the **20-second look-away** when it falls within a pose: a look-away that would overlap a 5- or 15-minute pose becomes that pose at the look-away's start (so no separate look-away renders or sounds there). It cascades — a look-away pulled onto a 5-minute pose that itself overlaps the 15-minute pose ends as a single 15-minute pose.
* **Example** (the user has taken no pause for 3 hours, so at `t0` everything is overdue; look-away times rounded — the 20 s length is omitted): one **15-minute** pause starting at `t0`, a look-away at `t0+35min` (20 min after the pose ends), a look-away at `t0+55min`, a **5-minute** pose at `t0+1h15`, a look-away at `t0+1h40` (20 min after that pose ends), a look-away at `t0+2h`, a **15-minute** pose at `t0+2h15`, a look-away at `t0+2h50` (20 min after that pose ends), and so on. (Each pose re-anchors the look-away to 20 min after it ends; the 5-minute pose that would fall near `t0+2h20` is re-anchored to 1 h after the `t0+2h15` pose ends.)
* **Scheduler interaction — a screen break is a period (§9), not an obstacle:** To the §9 scheduler a screen break is one of the **periods** the timeline is made of, and each of the three breaks says which period it is — they are exactly the periods of `side-dev`'s **test 11**, the reference case for a period that slides with the now-line:
  - the **20-second look-away** is one period accepting **nothing at all** (test 11's sliding 20 s window);
  - the **5-minute pose** is a closed **first minute** accepting **no task** — the minute the eyes need to actually leave the screen — followed by a tail accepting the tasks that need no screen **and** are marked **doable during a screen break** (§8). That is test 11's "1min: nothing" + "4min: only A" stretch, verbatim;
  - the **15-minute pose** is one period, open end to end, accepting **every task that needs no screen** (§8's "On screen" switch off) — with **no** closed first minute and **no** *doable during a break* gate. A quarter of an hour is not a stretch one has to be eased into, and it is long enough to be genuine off-screen working time rather than a pose to fill.

  In every case a task is placed only while its minimum time (§10) still fits what remains of the period. Everything else flows around it. The difference with a simple fixed panel: when a task panel gets cut by a screen break, the scheduler **does not consider that the task's minimum time is cut**. The task panel is split around the screen break and resumes after it, still accumulating its full minimum time — the screen break is inserted on top and never reduces the surrounding task's minimum. (Contrast §9/§10, where a regular fixed panel shortens the chunk.) That exception is deliberate and is the *only* one: without it, a look-away every 20 minutes would make any task whose minimum exceeds 20 minutes — the default is 45 (§10) — permanently unschedulable.
* **Display switch (calendar window):** a switch in the calendar window toggles whether the screen breaks are **drawn**. **Off by default.** When off, no screen-break blocks are shown, and **if two panels of the same task are separated only by a screen break that is now hidden, they fill the gap and merge into one block**. This is a purely **cosmetic** calendar choice — the real spanning time and the underlying schedule are unchanged. The switch state persists across sessions.
* **Notifications stay on:** screen breaks are **notified by a system notification when they come due** (named by their title — the look-away / pose), and this is driven from the schedule, not the display. **Hiding the screen breaks never silences their notifications.** If, at the **end** of a screen break, the next task panel is the **same task** as the one before the screen break (the common case — the user just resumes what they were doing), the "task to do now" notification does **not** re-appear; it appears only when a *different* task follows.
* **20 s look-away voice:** in addition to the notification, when the **20 s look-away** pause is reached a **voice** says to look 20 feet away, and 20 s later (the pause's end) says to resume work. A **toggle in the lateral menu** ("Look-away voice") enables it (on by default; persisted).
* **Manual look-away ("Look away now"):** a button in the lateral menu (§7) — and the system-wide `Ctrl+Shift+Alt+E` chord, which does exactly the same thing from any application — that is **always present** — a look-away can be taken at any moment, so its availability never depends on the state of the cadence (it used to be shown only while the most recent past screen break was a look-away). Pressing it starts the 20-second pause **now**: it supersedes any look-away cue still sounding or pending — including a look-away already running, which is then **erased from the calendar**, since it did not happen — announces and speaks the break, says to resume work at its end, and, **when its own 20 s are up**, **re-anchors the cadence** so the next look-away is one interval after this one (the calendar's break markers re-flow accordingly) and keeps it drawn where it was taken. Cut short in turn, it leaves no trace either: the cadence only ever moves for a break that finished. The cues are scheduled at the exact instant the now-line reaches each boundary, so they fire correctly even under time acceleration (§16). On the desktop the voice uses a local neural text-to-speech voice (Piper), falling back to the operating system's speech synthesizer. Unlike the 5- and 15-minute poses — whose completion the app detects from a device pause of at least their length — the app **cannot tell** whether the look-away was actually done, so it **always assumes it was** and just advances to the next look-away.
* **Break-finished voice across devices:** for an account signed in to cross-device sync, when **every device on the account has gone inactive** while a screen break is waiting to be served (and the account is not deliberately away — the Sleep/Work toggle, `ARCHITECTURE.md` §8), the **phones** speak at the break's **end** to tell the user the pause is finished and to resume work. There are **two ways this is detected, and each has its own server function**, differing only in what is known about the instant the user walked away. **(a) The device is cleanly locked** — the app is listening to the lock event, so it immediately sends one HTTP request to the function that **decides whether a data payload must be sent** (`pause-cue`); that function decides, computes the break's length and tells the phones to schedule the right vocal message at **the current instant + the break's length**, and marks the episode as sent. **(b) The device died without saying so** (killed, crashed, out of battery) — no such request is ever sent, so a server-side **pg_cron tick** (every `t_b`, 1 min by default) watches every account's presence rows and finds an account whose rows are **all** as old as or older than `2·t_a`; it then calls a **different function** (`pause-cue-cron`) which directly computes the break's length, sends the data payload and marks the episode as sent. Either way it is a **push notification to all the account's phones**, a high-priority data payload that neither it nor the vocal message wakes the app for; and either way the episode is marked sent exactly once, so the two can never both fire. On path (b) the walk-away instant has to be *estimated* as `t2 = <the last presence row's time> + t_a/2` (the midpoint of the tick interval the last device disappeared in); on path (a) there is nothing to estimate, because the request *is* the walk-away. Each of the two break types (`5min_break`, `15min_break`) has a **length and a vocal message that can be changed over HTTP** without a redeploy, as can `t_a` itself; a device reports **when both breaks next come due** — the account plus the two scheduled times of apparition, and nothing else — so which break is owed, and for how long, is decided server-side from that pair. (A debug override that retimes the *drawn* break therefore shortens only what the app draws and speaks locally; shortening the pushed cue's delay means changing that break type's length over HTTP, which is what the fast-break scripts do.) When **several poses are due at once** (all overdue at the now-line), the waiting break is the **longest** of them — resting it discharges every shorter pose due at the same instant (the merge rule above) — so e.g. having passed **both a 5-minute and a 15-minute** pose, the message fires **15 minutes** after the all-idle window starts, not 5. (With **four 15-minute breaks pending** since the last one taken it is likewise 15 minutes after the all-idle window starts — the user serves one 15-minute break and the rest re-project after it, §15 rules above.) The idle instant is the server-stamped moment the last device stopped reporting, so the cue time does not depend on when the server tick happens to notice; and a device that is **cleanly locked** tells the server so immediately, instead of waiting to be missed — which is also what makes its cue exact rather than estimated. A device counts as reporting only while it is **actively unlocked**, so the whole mechanism costs nothing while the user is away.
  * *Delivery when the app is backgrounded or killed.* Because a backgrounded phone can't reliably run an in-app timer (it stops sending heartbeats precisely when the cue matters), the cue is delivered via a push-triggered **OS-scheduled local notification/alarm**, so it fires even when the app is not running. The cue is **suppressed** if any device becomes active again before it fires — the user is already back at a screen and gets the ordinary break notification instead. Unlike the **look-away voice** (which the app always assumes was done), this cue exists precisely to call the user back to the screens they have left; it fires correctly under time acceleration (§16). The app is always connected to an account (core PRD §5) — a guest one counts — so the only case where this path is inactive is a device that could not create its account yet. *(The delivery chain — the `t_a` presence tick, the lock report to the `pause-cue` Edge Function's `evaluate_pause_cue()` decision, the `t_b` `tick_pause_cues()` pg_cron job and its `pause-cue-cron` Edge Function, FCM/APNs — is `ARCHITECTURE.md` §8 and the runbook `docs/PAUSE_CUE_DELIVERY.md`.)*
* **The screen breaks:**
  - "look 20 feet away" — 20-second look-away, due 20 min after the last one.
  - "take a 5min pose and blink hard" — 5-minute pose, due 1 h after the last one.
  - "take a 15min pose" — 15-minute pose, due 2 h after the last one.

## 16. Debug: time simulation
* **Debug-only:** A time-acceleration panel drives the scheduler from a virtual clock so the deadlines (§9), the calendar now-line and day rollovers, the device-sleep holes (§12) and the screen-break rhythm (§15) can be exercised in seconds instead of hours. It is **off by default** and **never appears in a release build** — only development runs enable it (the startup gating mechanism is `ARCHITECTURE.md` §7). The panel sits at the **bottom-left** of the content area, just right of the lateral menu.
* **Simulation, not reimplementation:** Every debug control **drives the same Intents and code paths as the real app** — it only changes the *source* of an event, never how the event is handled. Accelerating time merely makes the normal scheduler tick read a faster clock; **"simulate pause" instantly leaps the virtual clock forward by the whole break** so it elapses through the engine's own loops (the active-session beat, the schedule advance, the derived-pause seeding) with the chosen device(s) forced to read as screen-inactive across the jumped-over window — a break is exactly time in which the fixed-real-cadence heartbeat observes no activity, so the pause, the rested screen breaks, the derived no-screen period and the resumed schedule are produced by identical logic to a real ≥duration walk-away. No debug control carries its own copy of scheduler behaviour.
* **Controls:** speed presets (1× / 10× / 60× / 300×) and a pause (0×) that re-anchors so changing speed never makes the clock jump; **"simulate pause + leap"** of a chosen duration (20 s / 5 min / 15 min) that **instantly jumps the now-line forward by the whole break** (rather than gliding there), with an **"inactive:" dropdown** choosing which device(s) live the pause as screen-inactive — **all**, **only the computer**, or **only the phone** (the phone options appear only while a phone is on the debug time-link); and **"reset to real time"** that snaps back to 1× real time.
* **No pollution of real data:** Because the virtual clock runs ahead of real time, a change committed while it is diverged would otherwise persist future-dated data. Such changes are flagged and **reverted at the next app start** (a warning shows while any are pending), so a debug session never leaves future-dated records or schedule changes in the saved state. The revert reuses the Undo/Redo engine (§6).

## 17. Sleep schedule
* **Purpose:** A nightly **sleep window** the scheduler treats as unavailable — neither the §9 task fill nor the §15 screen-break projection places anything while the user is asleep — and which the calendar shows.
* **Sleep window (settings):** A floating **"Sleep"** window, opened from a lateral-menu button (§7), with three fields:
  - **Wake time** — when the user currently wakes (default **07:30**).
  - **Goal wake time** — the wake time to drift toward (default **07:30**).
  - **Total sleep time** — the bed-to-wake duration (default **8h30**).
  The sleep window each night is `[bedtime, wake)` where **bedtime = wake − total sleep time**, so with the defaults it is **23:00 → 07:30**.
* **Wake drift:** The current wake time **shifts 15 minutes toward the goal every 2 days**, counting from the day the settings are saved, until it reaches the goal. The total sleep time stays constant, so **bedtime drifts with wake** (the whole window moves earlier/later together). The drift is computed per day, so the window can differ from one day — and one week — to the next.
* **Scheduler avoidance:** The sleep window is a fixed obstacle to the §9 task fill (a task that meets it is **split and resumes at wake**, not charged for the sleep time — like a screen break, §15) and to the §15 screen-break projection (a look-away/pose that would fall in the window is **skipped and its cadence resumes at wake**). No task panel and no screen break occupies the sleep window.
* **Wind-down before bed:** **No task** is scheduled in the **hour before bedtime** (the sleep obstacle extends one hour earlier for the task fill). Screen breaks may still occur in that hour. When the now-line reaches the start of the wind-down hour, a **"Stop work" system notification** fires (scheduled at the exact instant, so it is correct under time acceleration §16).
* **Calendar display:** Each night's sleep window renders on the calendar as a labelled **"Sleep"** band behind the task blocks, and it **cuts** the task blocks before and after it (a task that stops at bedtime and one that resumes at wake render as separate blocks, even when same-task display merging would otherwise bridge the gap). The calendar's **default zoom** fits the awake part of the day around it (§8).
* **Carved by activity (worked-through nights):** Where the user was **active** on a device during a scheduled sleep window — i.e. still working when they were meant to be asleep — the **"Sleep" band shows a gap** for that stretch rather than a solid block, so a night worked through reads as awake time. The gap is derived from the account-wide activity (§15 pauses) plus this device's live session, so while the user keeps working it retracts to the current time. This is display-only (the scheduler still treats the whole window as sleep, §9/§15) and, being derived per device, is never persisted or synced on its own. Absent any activity evidence — future nights, or a night with no recorded sessions — the band stays solid.
* **Defaults & persistence:** Production starts with the default schedule (07:30 / 07:30 / 8h30, i.e. a 23:00–07:30 window) until the user edits it; the schedule (and the drift anchor) is persisted across sessions.
## 18. Alarms
* **Purpose:** Plain wall-clock **alarms** (an alarm clock), independent of the schedule: at the time the user sets, **every device signed in to the account rings** — every phone, and any desktop that is running. Unrelated to the §15 screen breaks (which are driven by work rhythm and presence) — an alarm is a fixed time of day the user chose.
* **Alarms window (settings):** A floating **"Alarms"** window, opened from a lateral-menu button (§7), listing the account's alarms — one row each, added with **"+ Add alarm"** and removed with the row's bin button. Per row:
  - **Time** — the wall-clock time of day it rings (`HH:MM`).
  - **Label** — optional text, shown on the ringing device.
  - **Rings for** — **how long the alarm sound lasts**, in seconds (default **30 s**, max 10 min). The vibration, when on, lasts the same time.
  - **Vibrate** — whether the ringing phone also **vibrates** (ignored on the desktop, which cannot).
  - **Days** — **the days the alarm is triggered on**, as seven toggleable weekday chips (Monday-first). **By default it is every day.** The last selected day cannot be turned off (an alarm always has a day to ring on — use **On/off** to silence it instead), so an alarm never silently rings nowhere.
  - **Repeat** — on: it comes round on each of its days; off: it is a one-off and **disarms itself** once it has rung (the row stays, ready to be re-armed).
  - **On/off** — arms or disarms the alarm without deleting it.
  Rows are edited live: every change is saved and synced immediately.
* **Shown on the calendar (§8):** Every ring of every armed alarm is drawn on the calendar at its instant, as a small marker in its own colour (an alarm has no duration, so it is not a height-proportional block, and it is deliberately unlike the blue task/reminder chips — it is not work). It is **inert**: unlike a reminder there is nothing to check off, and unlike a panel there is nothing to drag, resize or edit there — the Alarms window owns it. Because a ring is a **fixed** wall-clock instant, a ring that has already gone off stays where it happened rather than following the now-line, and only the days the alarm is triggered on get a marker. The markers are computed for the **displayed week only** (§9 "the horizon follows what is displayed"), so navigating to another week draws that week's rings.
* **Rings on every device of the account:** The alarm list — its times, **its days**, and the rest of each row — is **authoritative** user data (§6), persisted and synced to every device, and each device decides its own ring from that list. Editing an alarm on one device changes when every device of the account rings, and on which days.
  - A **phone** arms the ring with the OS, so it rings **offline**, while the phone is dozing, and with the app backgrounded or killed; a phone that was off re-arms when it comes back.
  - A **desktop** has no OS alarm clock, so it rings from its own now-line while the app is running — which is the only time it could ring anyway. A ring the machine slept straight through is **not** replayed on wake (a missed alarm stays missed rather than sounding at the wrong time).
* **Ringing:** The alarm sound is an **acoustic guitar** — a plucked arpeggio, looping for the configured length. It is the **same sound on every device** (the app synthesizes it itself rather than using each device's own ringtone), so an alarm is recognizable wherever it goes off. The phone plays it on the alarm audio stream (vibrating alongside it when asked; if the phone cannot play raw sound it falls back to its own alarm ringtone rather than staying silent) and shows an **Alarm** notification with a **Stop** action to silence it early; the desktop plays the same loop for the same length and shows the same **Alarm** notification (no Stop action — it ends by itself). Either way the ring is logged like any other notification (§11). On the phone only the **soonest** ring is armed at a time; when it fires, the next one is armed.
* **Exactness:** The ring instant is the fixed wall-clock instant `time of day` on each local day **the alarm is triggered on** — so an alarm keeps its displayed time across a daylight-saving shift — and it is a pure function of the calendar, never of when the app happens to tick. Under time acceleration (§16) the phone's armed instant is converted to the real time at which the simulated instant is reached, and the desktop's sweep fires on the simulated instants the clock crossed.
